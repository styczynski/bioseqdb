What PostgreSQL encryption at rest actually protects

Follow a specimen record from a SQL query to an encrypted file, and see where pg_tde, key management, WAL and backups fit into the picture.

12 October 2026·5 min read·Piotr Styczyński
Markdown

Suppose I keep specimen identifiers and laboratory notes in PostgreSQL. A copy of the database directory ends up on a misplaced disk, while the database itself is still running somewhere else. I want the copied files to be unreadable, but I also want the application to carry on using ordinary SELECT statements, without adding a decryption call to every query.

That is the useful part of transparent data encryption, or TDE. The word “transparent” describes the application's view: storage can change while SQL still returns the original values. It does not mean those values stop being sensitive once the server has read them.

Follow the record, then choose the boundary#

An authorised database session needs readable rows to filter and return results. Encrypting stored files therefore does not stop that session from reading a specimen note, nor does it conceal the note from a fully compromised running server. The connection needs its own protection, normally TLS, and database permissions still decide who can issue the query. PostgreSQL describes these separate layers in its encryption options.

I find it easier to draw this boundary before choosing an extension, because “the database is encrypted” says very little about a CSV export sitting beside it, an application log containing query results, or the person holding a database password.

Where pg_tde fits#

This example refers to pg_tde 2.2.2, using its documented configuration as of October 2026. It requires the changes in Percona Server for PostgreSQL; installing the extension package into an arbitrary community PostgreSQL build is not an equivalent setup. The supported deployment list covers Percona Server 17.5 and later, while the PostgreSQL 16 build is a technology preview.

This is a general PostgreSQL example. It does not establish compatibility with BioseqDB's own table access method.

For a table created with USING tde_heap, the extension covers its stored data, indexes and associated TOAST data. TOAST matters here because a long specimen note may live outside the main table's pages. Column names and other table metadata remain visible. See the documented encrypted data scope.

There is another distinction which is easy to miss: a temporary table and a temporary file produced by a large sort are different things. Version 2.2.2 leaves query spill files and PostgreSQL's system catalogues unencrypted, including statistics. Those are meaningful limits when the aim is to protect patient information, so disk protection may still have a separate job to do. The limitations page is part of the design, not something to read after deployment.

On the encryption side, the principal key protects internal keys, and those internal keys protect the stored files. Keeping the principal key in an external key service separates it from the files it unlocks. A copied database directory should not arrive with everything needed to decrypt it. A local file provider can help with a disposable experiment, but its key file is unencrypted; the keyring guide recommends proper key management for production.

WAL and recovery need their own plan#

Table encryption alone does not settle the write-ahead log. WAL encryption became generally available in pg_tde 2.0, after some early introductions were written. It has a separate server-wide configuration, covers writes from all databases in the cluster, and needs a restart when enabled. Existing plaintext WAL does not become encrypted retrospectively. Follow the current WAL instructions, including their required archive and restore wrappers.

A logical dump is another copy of readable data: pg_dump reads through PostgreSQL's client interface, rather than preserving encrypted relation files. Protect the resulting dump separately. The SQL dump documentation explains that distinction in how the backup is made.

For physical backups, I would make recovery the acceptance test: restore elsewhere, recover the required keys, replay WAL, and check the specimen rows. Percona's backup procedure specifies the encryption metadata and provider files needed, and warns against rotating keys during a backup. It is a seperate operational dependency worth rehearsing before there is an incident.
