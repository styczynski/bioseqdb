Working with sequence files in BioseqDB and SeqKit

Import mitochondrial DNA from UCSC into PostgreSQL, then compare BioseqDB SQL with SeqKit for sequence statistics, GC content, motifs, slicing, sorting and FASTA housekeeping.

19 October 2026·23 min read·Piotr Styczyński
Markdown

A FASTA header can carry quite a lot of information. The sequence has a name, somebody adds an organism, then an assembly and perhaps some coordinates, and eventually you need a little regular expression just to recover something that could have been a column in a table.

A FASTA record starts with a header line beginning with >, followed by the sequence letters on one or more lines.

I like having those columns. This is one reason I wanted sequence operations inside PostgreSQL when I started working on BioseqDB. You can keep the DNA next to its metadata and write a query that uses both, without exporting another intermediate file every time you change a filter.

SeqKit's tutorial has plenty of useful examples of the work people do with sequence files. I picked several of them and some tasks from the FAQ to try in SQL: checking lengths, counting bases, finding motifs, selecting records and dealing with names.

We will use the same sequences in both tools. I checked the examples with SeqKit 2.14.0 and a BioseqDB development build with external database support. You can find the SQL, shell commands and chart code in BioseqDB/examples/seqkit_workflows.

1. Get a small dataset from UCSC#

For this exercise I chose three mitochondrial chromosomes: human, mouse and zebrafish. Mitochondria have their own DNA, separate from the much larger nuclear chromosomes, so we get complete chromosome records small enough to inspect without waiting for a large download. These three records total 49,464 bases.

Our source is the UCSC Genome Browser API. BioseqDB's external tables can fetch sequence intervals from UCSC directly through SQL. We will use assembly names hg38, mm39 and danRer11, each with chromosome chrM.

Warning

Availability on 16 October 2026. The published 0.1.0-alpha.1 Docker images and native package builds omit the external-database integration used here (due to my oversight). It is planned for the next alpha release, but you can obviously compile source from Github directly. Currently using runtime SET, an API key, or a GRANT won't work as the code isn't present in the binary - when building one must use BIOSEQ_BUILD_EXTERNAL_API_CLIENTS=ON to enable this feature.

4. Count bases and calculate GC content#

GC content is the percentage of known DNA bases that are G or C. A sequence with 30 Gs and 20 Cs among 100 known bases has 50% GC content. We can calculate it for a whole chromosome or for smaller windows to see where its base composition changes.

Mitochondrial DNA is circular, so a search across the chromosome's origin also needs a sequence slice joining its last bases to its first bases.

strpos returns the first occurrence using PostgreSQL's one-based string positions. Subtracting one converts it to a zero-based offset inside the window. SeqKit reports one-based inclusive start and end coordinates, so a SQL offset of 120 corresponds to SeqKit start 121. Add the window's start0 to get the chromosome offset.

There is one GAATTC occurrence in each of these eight matching windows, so both listings return eight positions. With repeated occurrences in a window, strpos returns the first one and seqkit locate returns all of them.

We can make a copy with its fifth base set to T:

SeqKit

PostgreSQL's text function overlay uses one-based positions, so from 5 for 1 agrees with seqkit mutate -p 5:T. This SELECT returns the edited twenty-base text beside the original while leaving the stored sequence unchanged. Cast a complete edited string back to bioseq.seq('dna5', 64) when you want to store it as DNA.

SeqKit's concat joins sequences with matching IDs across files. We can do the same with a SQL join:

BioseqDB

Executed against Bioseq extension 1.0 on PostgreSQL 17.10

SeqKit

Here left.fa contains the first ten bases of the first three human windows, and right.fa contains their last ten bases with the same IDs. The repository's seqkit.sh script prepares those files. The SQL common table expressions prepare the same two inputs, then JOIN ... USING (id) pairs them. OPERATOR(bioseq.||) concatenates the BioseqDB sequence values. The result is a twenty-base sequence containing the two ends of each window.

seqkit rename adds suffixes to repeated IDs, while seqkit rmdup -s compares sequence contents. To try both, seqkit.sh creates three records in duplicates.fa: two records share the ID copy, the second has an edited final base, and the third has ID other but repeats the first sequence exactly.

For that input, seqkit rename duplicates.fa returns IDs copy, copy_2, other. In SQL, number the rows within each ID using row_number() OVER (PARTITION BY id ORDER BY ordinal) and append the number after the first occurrence. Keep an input-order column such as ordinal if the identity of the first record matters.

To remove repeated sequence contents, seqkit rmdup -s -P -i duplicates.fa retains the two distinct sequences. PostgreSQL's DISTINCT ON (seq) does the same forward-strand grouping, with ORDER BY seq, ordinal choosing the first copy. -P restricts SeqKit's comparison to the forward strand, matching the SQL grouping. The complete runnable queries for both operations are in 03_queries.sql.

For an exploratory subset in SQL, you can write ORDER BY random() LIMIT 5. Re-running it changes the sample. Here we use a fixed ordering derived from each ID and the label '2026:', so you can repeat the query and get the same five records:

Changing '2026:' changes the SQL ordering. Remove LIMIT 5 to reorder all rows using the same method. SeqKit has shuffle -s 23 windows.fa for a seeded shuffle and sample -p 0.1 -s 11 windows.fa for a seeded fraction sample.

The SQL example returns exactly five rows. SeqKit's -p 0.1 gives each record a 10% chance of inclusion and returned six rows on this input with seed 11. The chosen IDs differ because these are two different ways of selecting a subset. For sampling a fixed number from large files, read the SeqKit sample documentation and its notes on the count option.

For me the useful difference appears when the next question involves metadata. Once the sequences are in seqkit_lab.windows, adding a species condition or joining a list of interesting regions is an ordinary SQL query. The data stays beside the information explaining where it came from. SeqKit remains convenient when I need to inspect or transform a file from the terminal, and the FASTA export means I can use it on exactly the same records.

For a comparison of longer regions that allows substitutions, insertions and deletions, try the BioseqDB alignment tutorial. The queries there return matching intervals you can plot, along with the species and coordinate columns used throughout the analysis.
