Configuration reference (settings available in BioseqDB)

This appendix lists all runtime settings registered by BioseqDB (GUCs - GUC stands for Grand Unified Configuration in Postgres and refers to runtime parameters) - their types, defaults, possible values and descriptions. Each setting can be viewed and set with the SHOW and SET commands [118, 119]. Some settings are hidden so they’re not visible with SHOW ALL.

Physical storage settings.

GUC name Type GUC values Description
bioseq.storage.compression.algorithm enum

zstd

(default)

 Choose the compression algorithm used for storing data columns Use Zstandard when compiled in. This is the preferred build-time default. Changing the default does not rewrite any existing indices!
none Store column chunks without compression.
pglz Use Postgres built-in coded. This becomes the default when neither of previous two is available.
lz4 Use LZ4 when compiled in. This becomes the default when Zstandard is unavailable.

3

(default)

1…19

 Set the zstd compression level if zstd is used.
bioseq.storage.stripe.row_limit int

150000

(default)

1000…100000000

rows

 Sets the maximum rows in a new table’s column stripe, when writing rows. Existing table options and stored stripes are unchanged.
bioseq.storage.chunk_group.row_limit int

10000

(default)

1000…100000000

rows

 Sets the maximum rows in a new table’s chunk group, when writing rows. Chunk groups divide a stripe into smaller column-reading units.

bioseq.storage.dml.enabled

hidden

 bool

on

(default)

 Special setting that controls whether reads apply deleted-row masks. Default, shouldn’t be changed. Normally deleted rows that are marked as such, should not be returned in queries.
off Bypass any deletion filtering. Useful for debugging, the queries will return all rows including deleted ones. Note that if the table is rewritten using VACCUM FULL, then deleted rows will physically dissapear!
bioseq.column_cache.enabled bool

on

(default)

 Controls the backend’s decompressed column-chunk cache. After decompression save the buffer, so it’s avaialable for reuse Decompression cache only applies to one query. After completion of the query, the cache is cleared.
off Read and decompress but do not save buffers in cache.
bioseq.column_cache.capacity_mb int

200

(default)

20…20000

MiB

 Limits the decompressed column-chunk cache BioseqDB will still allocate buffers for decompression, so this setting does not control the total memory used during decompression
bioseq.load.write_overlap.enabled bool

off

(default)

 Experimental setting to use parallelized writing and decoding of data chunks through queue when loading FASTA/FASTQ files. Default reader perform decoding and writing (placing sequences in buffer) sequentially.
on Enable parallelized writing and decoding of data chunks through queue.

bioseq.storage.sequence_shard.max_size_gib

superuser

 int

1024

(default)

0…2147483647

GiB

 Sets the sequence-shard size limit. If the shard table exceeds that size, then new table will be created. Setting it to 0 means that each sequence is stored in a separate table (useful for debugging, but extremally ineffective in practice)

Planning and execution#

Planning and execution settings.

GUC name Type GUC values Description

bioseq.execution.parallel.enabled

hidden

 bool

on

(default)

 Enable Postgres parallel queries Allow possible parallel scan paths (actual worker availability still depends on PostgreSQL planner, so this setting does not force the planner to use parallel scans). Additionally, any query using mmsearch won’t be parallelized, due to current code architecture. The parallel scans however are possible for metadata queries. Alignment won’t use parallel scans even with this setting enabled.
off Disable all parallel scans on BioseqDB tables.
bioseq.execution.parallel.minimum_processes int

8

(default)

1…32

 Requests the PostgreSQL worker count for possbible Bioseq parallel scan paths. This is soft minimum and the actual worker count is determined by the PostgreSQL planner.

bioseq.vectorization.enabled

hidden

 bool

on

(default)

 Can disable vectorized SQL operations for aggregates like SUM(), COUNT(), etc. Use supported vectorized SQL operations when the plan allows them. Vectorized operations only apply to non-sequence aggregates, not alignment pipeline.
off Use normal SQL processing for those operations.

bioseq.planner.index_scan.enabled

hidden

 bool

on

(default)

 Can allow usage of non-BioseqDB indices with BioseqDB tables. Allow using non-BioseqDB indices during queries, for example it becomes possible to use B-tree index on metadata column. This settings does not control any BioseqDB indices like MPF/MPS etc.
off Do not allow using any non-BioseqDB indices on BioseqDB tables. This can heavily degrade performance as Postgres will select plan that ignores existing B-trees, hash indexes etc.

bioseq.planner.custom_scan.enabled

hidden

 bool

on

(default)

 Entirely disable all BioseqDB custom scans. Allow the planner to install Bioseq custom scans. Useful to force Postgres to select non-BioseqDB plans. Do not use this unless you know what you’re doing.
off Disable custom scans. This means that it won’t be possible to use ’mmsearch’ function anymore as it requires custom scan path. All other metadata queries still will be possible.

bioseq.planner.custom_scan.max_paths

hidden

 int

64

(default)

1…1024

 Limit paths explored by GQO for BioseqDB custom scans. Increasing the number may yield better plans, but increase planning time.

bioseq.planner.qual_pushdown.enabled

hidden

 bool

on

(default)

 Controls behaviour of predicate pushdown. Normally filters can be pushed down into the scan, which improved performance. The predicates that Postgres reports as highly-correlated will be used to possibly reduce number of loaded chunks (min/max prunning mechanism) Pushdown uses correlation statistics for column reported by Postgres to decide if this predicate can be useful to avoid loading chunks
off Leave predicates outside the scan, which may severely degrade performance.

bioseq.planner.qual_pushdown.correlation_threshold

hidden

 real

0.4

(default)

0…1

 Sets the minimum absolute column correlation value (reported by Postgres table statistics) used by chunk prunning logic described for bioseq.planner.qual_pushdown.enabled. Values closer to one, mean stronger correlation.

bioseq.planner.sequence_sort_scan.enabled

hidden

 bool

off

(default)

 Enable or disable custom sort for BioseqDB sequences. Sort works only if there’s single sorting key that is sequence column itself. Use default Postgres sort.
on Consider the custom batch-sort where possible.

off

(default)

bioseq.index.sequence_read.enabled bool

on

(default)

 Controls whether the pipeline executor can read indexes. If the option is disabled, then pipeline will always recompute all seeds from scratch. Normally allow reading BioseqDB indices. bioseq.index.async_persistence.enabled bool

off

(default)

 Very experimental setting that allows main process to asynchronously update missing indices for sequences: If query does not have seeds in index for certain sequence and needs to compute them, after the query the index will be updated. Do not stage asynchronous persistence work. Grouped MPF index (default) does not implement this feature and using it with this option enabled will produce an error. Additionally you need to enable bioseq.index.recompute_async_persistence.enabled as well.

 Separate setting, but effectively to enable async persistence you need to enable bioseq.index.async_persistence.enabled together with this one. Same as bioseq.index.async_persistence.enabled Set bioseq.index.async_persistence.enabled to the same value as this one.

Per-search options#

Additionally instead of operating on global settings, user can also provide single object as third parameter to the mmsearch function call.

Note

Parameter encoding

Currently the enum options are encoded by integers - they correspond to the global GUCs, but you can use only numbers. This is just unimplemented feature - the types of the options should be changed to strings and encoded to internal enum int values. It was requiring less effort to expose internal representation, so it was left as is, see listing below configuration options.

The index-read requirement#

This is special field that has no GUC equivalent, that is only available via aligner_options. This is special flag very useful during testing and controls how index reader behaves.

Special option controling index reader

Options field Type Value Description
index_read_requirement int

0: allow

(default)

 If no compatible index is available, seeds can be recomputed from scratch. This is the most useful in practical sense as it allows the largest flexibility for user.
1: require_absent Never read index even if it exists, always recompute seeds from scratch. Additionally setting this option will produce errors if deffered index update is ON. Practically used in testing scenarios to see what happens if index does not exist.
2: require_compatible_persisted Hard requirement that index must allways exist. If the index does not exist or is incompatible (different k/w parameters etc.), the query will produce error before execution.
