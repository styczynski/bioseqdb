\section{Reading only what the algorithm requires}
\label{sec:lazy-sequence-facade}
\label{sec:sequence-materialization}

The storage can be provided in different forms as explained previously in the first section~\ref{sec:sequence-abstractions}
In BioseqDB main implementation of Postgres-based storage is done via \path{lazy_sequence_view<A>} and \path{retained_lazy_sequence_view<A>} mentioned in table~\ref{tab:sequence-representation-specializations}.
These types holds pointers to functions that implement the storage and represent the following operations:
\begin{itemize}
  \item Report sizes of sequences
  \item Copy selected intervals into caller-owned memory, which in this case can be GPU-owned memory in GPU-accelerated pipeline stages
  \item Reading successive chunks
  \item Checking if the compatible interval was already materialized and can be borrowed (caching)
\end{itemize}
Internally I distinguish several access policies which are specified by the pipeline stage, they are the following choices:
\begin{enumerate}
  \item \textbf{Stream.} If the algorithm accepts a stream, read the selected
        interval in bounded chunks and save it to reusable scratch memory (large memory pool)
  \item \textbf{Borrow.} If the algorithm needs packed data, first check if's already in cache and safe to borrow.
  \item \textbf{Pack.} In case if borrowing is not possible, algorithm needs to request new memory permit (this is routed through custom pool allocator). Caller is then responsible for this memory chunk.
\end{enumerate}

At this point I need to describe lifecycles of various entities to illustrate how reading is performed.
Figure~\ref{fig:sequence-scan-lifecycle} shows how what is happening under the hood during the scan:
\begin{itemize}
  \item (a)~Each row of a batch gets its own scanner with 16 fragment slots for caching. A miss looks in the decoded chunk cache
  (this is lower-layer cache for sequences chunks which may store multiple unrelated sequences and is discussed in later chapters),
  then in the columnar relation, and copies one fragment into a slot.
  \item (b)~The incoming queries are grouped in batches. Each batch has it's own session, which is destroyed when batch processing is finished.
  The session is different entity to the chunk cache so relation isn't reopen when batch is finished and we keep large sequence chunks still in memory.
  At the start of the batch the backend first builds one packed copy in memory and distributes that copy to workers from the pool.
  It's important that in this architecture we only have one backend thread which is responsible for reading relation.
  This means that the actual pipeline is run by single thread that submits various work to worker pool.
  I needed to read the relation on a single thread to avoid race conditions on PostgreSQL's process-local state which is not thread-safe -
  PostgreSQL starts (forks) a new server process for each client connection, and even parallel SQL starts extra background worker processes rather than extra threads inside the 
  same backend~\autocite{postgresql17_tutorial_arch,postgresql17_how_parallel_query}.
  The same read could still be done in parallel by giving each reader its own backend: one way would be to fork a background worker with a database connection
  (which in this context is problematic as forking with pool running will result in segfaults) 
  or open a second client session through libpq (libpq is thread-safe when each thread uses its own connection)~\autocite{postgresql17_bgworker,postgresql17_libpq_threading}.
  I did not take those paths for fragment reads during a query as it would complicate the implementation and this is something to be done in the future.
  \item (c)~A view is built from two pointers - \texttt{state} is a piece tree together with the session that holds one scanner per source row and \texttt{ops} contains length, two flags and 
  two function pointers. Providing function pointer serves as abstraction layer to divide non-Postgres code with actual Postgres implementation.
  Using templated types could be possible here, but they still would need type erasure.
  A retained view additionally holds a release callback (C-style destructor)
  \item (d)~At every batch end, in this order: (1)~release retained views, (2)~finish each scanner so its slot copies go, (3)~drop the session's memory.
  The worker pool and the snapshot naturally outlive the batch as discussed here.
  It might happen that we encounter an error and failing query skips C++ destructors, so steps 1--3 also run from a memory context callback (retained view release callback)
\label{lst:sequence-scan-lifecycle-steps}
\end{itemize}


Panel~(d) of Figure~\ref{fig:sequence-scan-lifecycle} has a gap between the end of batch~1 and the start of batch~2.
In that gap the backend collects the next tuples from the relation (metadata and sequence locators, not entire sequences), applies the query's \texttt{WHERE} clauses, and places surviving tuples in the dispatch buffer.
When enough tuples are collected, it submits the next batch.
That collection still uses one relation-reading thread per PostgreSQL process.
There's however support for \path{bioseq.scheduler.postgres_parallel.enabled} for any query that do not use alignment. 
The reasoning behind that is that only the thread pool wasn't designed around being multi-process safe and current statistics collection doesn't support it.
The scans that do not use alignment are marked parallel-safe. This means that example shown on lsiting below~\ref{code:simple-table-read-with-slice} can be executed by postgres parallel scan.

Scans in details are covered in the next chapter~\ref{sec:postgres-custom-scan-scope} in detail.
