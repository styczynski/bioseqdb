\section{Designing sequence abstraction}
\label{sec:sequence-abstractions}

Suppose user stores large genome sequence in one row, but only wants to align specific small part of it (let's say we know location of one protein-coding human gene and are interested only in finding occurences of that gene).
It would be very wasteful if I didn't provide built-in functionality to load only that small region. This region could be stored on disk, so we only have it's locator poiting to a specific chunk in the table.
On the other hand, we can load sequences from fasta file, where parser can be writing to RAM, so our sequence could refer to location in memory, where all sequences are pooled into one memory region to avoid constant allocation/reallocation.
In yet another case, in tests we would like to use standard library containers to prepare and examine sequences (potentially even somebody could directly call some internal BioseqDB functions as standalone alignment library).
This created a design challenge: same sequence can arrive as relationship locator, region in memory pool in RAM, can be provided as a whole as standrad container or as only a fragment (if user wants to operate only on specific slice or if it does not fit in RAM or RAM is limited, so we cannot fit entire sequence directly there), while
these fragments should also be shareable, so parallel alignment to the same sequence doesn't have to load them multiple times.


There are several existing libraries for interfacing with genomic sequences.
SeqAn\autocite{REINERT2017157,seqanManual} is a C++ library that provides modern interface for composing efficient sequence-analysis
software from generic C++ components. Its library includes sequence
representations, indexes and configurable alignment algorithms, with SIMD
alignment, but it has it's own limitations. However SeqAn SIMD algorithms are mostly limited to auto-vectoriztion provided by the compiler (which doesn't have to be portable in most cases) and offers very narrow set of features for custom pipelines.
I would be hard to directly reuse it for implementation of mentioned feautres. Using SeqAn would require deep integration, that's why I decided to address the design challenges by designing 
own C++ system of templates with different specializations driven by C++ concepts (inspired by nice-looking HPC MPI code~\cite{uhl2026conceptspracticecmpi}).

\info{SeqAn compatibility}{
  Because the architecture of BioseqDB pipeline is very custom, I decided to only use SeqAn's alphabet layer~\autocite{seqan3AlphabetsDocs} and utilities exposed by its public API. This means that libraries using SeqAn code as base, could be slightly adjusted to be able to work with BioseqDB pipelines.
}

SeqAn offers abstractions over lazy sequences as well~\cite{seqanSequencesInDepth}, but they're not as sophisticates as in my case.

\section{Packed symbols and a common C++ interface}
\label{sec:compact-sequence-range}
\label{sec:sequence-bit-layout}

The template-driven design allows usage of any arbitrary alphabet for sequences, though for now I only support DNA4 and DNA5.

Sequence is encoded using bitpacking - the symbols are converted into integers values with specified fixed number of bits per symbol, then several symbols are packed into one single storage unit. Storage unit can be integer of any physical size.
This is generalisation of bitpacking strategies commonly used in other software like packed-seq~\cite{packed_seq_library} Rust library developed by author of SIMD minimizers paper. packed-seq Rust library offers non-alphabet-generic packing~\cite{packed_seq_docs}.
My design was more inspired by SeqAn approach where packing container is available, but very limited in features~\cite{seqanManual}.

SeqAn alphabet assigns each symbol an integer called its \emph{rank}. For DNA4,
the four ranks are \(A=0\), \(C=1\), \(G=2\), and \(T=3\). A rank is an
encoding of a symbol. Each \path{compact_sequence_range<R>} type needs to know certain properties of the encoding that are held (using CRTP) in \path{compact_sequence_range<R>::traits} type. 
In my storage symbols never spill to other storage units i.e to retrieve some symbol you always need to access at most one storage unit.
The symbols in the storage unit are always packed in "little-endian" order i.e the first symbol is in the lowest bits of the storage unit and the last symbol is in the highest bits.
The properties in traits type are either types or constexpr static expressions/functions:
\begin{itemize}
  \item \path{alphabet_type} - type of the alphabet
  \item \path{storage_unit} - type of the underlying storage unit (usually \path{uint8_t}, \path{uint16_t}, \path{uint32_t}, \path{uint64_t})
  \item \path{alphabet_size} - number of symbols in the alphabet
  \item \path{unit_width} - width in bits of the storage unit: \(\text{sizeof(storage\_unit)} \times 8\)
  \item \path{bits_per_char} - number of bits per symbol: \(\left\lfloor\log_2(\text{alphabet\_size})\right\rfloor\)
  \item \path{letters_per_unit} - number of symbols that can be packed into one storage unit: \(\left\lfloor\frac{\text{unit\_width}}{\text{bits\_per\_char}}\right\rfloor\)
  \item \path{unit_used_bits} - number of bits used in the storage unit (for alphabet sizes that are not a power of two, some bits must stay unassigned): \(\text{letters\_per\_unit} \times \text{bits\_per\_char}\)
  \item \path{unit_leftover_bits} - number of bits leftover in the storage unit: \(\text{unit\_width} - \text{unit\_used\_bits}\)
  \item \path{char_mask} - mask for the last symbol in the storage unit
  \item \path{rev_char_mask} - mask for the first symbol in the storage unit
  \item \path{used_storage_mask} - mask for the used bits in the storage unit
  \item Conversion functions for converting between storage unit and symbol: \path{letter_to_symbol}, \path{letter_to_char}, \path{letter_complement}
  \item Utilities for generating k-mer masks: \path{kmer_mask}
\end{itemize}

\warn{Template instance explosion}{
  In BioseqDB I tried to allow user to specify any storage width that is power of two (8, 16, 32, 64) and alphabet (currently supported is DNA4 and DNA5). Because both of parameters are constexpr template parameters, this leads in some parts to creation of hundreds separate versions of pipeline.
  This slows downs compilation times and led to creation of absurdly large BMIs resulting in multi-gigabyte Clang \text{.pcm} files. Resulting binary still is optimised down to more convenient size, however I put lots of burden onto the compiler and linker.
  The goal of user-supplied storage widths was to observe how they affect performance and if they affect it at all. Currently in some parts of the pipeline I still cast the stored types to \text{uint32\_t}, this happens because some algorithms like SIMD chaining require
  larger widths to store indices and scores. Extracting  symbols directly from storage unit is a complex process involving lots of bitwise operations, so at this time most algorithms (SIMD/GPU) cannot operate directly on packed sequences as this would require lots of additional engineering effort.
  I added conversion helpers like one presented in the listing below~\ref{lst:compact-range-interface} that convert requested ranges of sequence into non-bitpacked sequence that is easier to work with.
  This operation is done on demand and stored in separate memory pool region, so pipeline doesn't have to convert sequence from bitpacked to non-bitpacked format multiple times.
  Directly unpacking sequence inside pipeline at the latest point in time is potential opportunity for future improvements.
}

\begin{BioseqCppSnippet}[caption={A consumer requests only the ranks it needs.},

template<supports_compact_sequence_range R>
void read_fragment(const compact_sequence_range<R>& sequence,
                   std::size_t first, std::size_t last,
                   std::span<std::uint8_t> output) {
    // One rank per output byte, in forward order.
    sequence.template to_encoded_into<false>(output, first, last);
}
\end{BioseqCppSnippet}
