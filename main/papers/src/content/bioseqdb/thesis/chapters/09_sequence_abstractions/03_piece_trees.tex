\section{Composing sequences without joining their payloads}
\label{sec:sequence-piece-tree}

The slice model I showed is very primitive. If we add ability to concatenate sequences we can represent any slice as a tree of pieces that represent operations on original sequence.
In BioseqDB this tree refers to Postgres operators and datums.

The slice tree is constructed from the following elements:
\begin{itemize}
  \item A \textbf{source leaf} describes interval in the source sequence.
  \item A \textbf{literal leaf} holds literal value referencing Postgres datum with additional metadata.
  \item A \textbf{branch} node that represents concatenation of two children. It holds total length, piece count (total number of leafs in subtree) and tree height. We collect total length to estimate how long the memory region in the pool should be to accomodate the materialized sequence.
  \item An \textbf{edge} that connects a node to its child. It holds reverse and complement flags, which affect the order of traversal and the interpretation of the leafs.
\end{itemize}

Figure~\ref{fig:piece-tree} illustrates concatenation of three pieces including two source leaves and one literal leaf:
\[
  Z=S[2,6)\ \Vert\ \operatorname{reverse}(S[8,12))\ \Vert\ \texttt{AC},
\]
The result is \texttt{GTAAATTGAC}, with length \(4+4+2=10\).

Each of the operations can easily be implemented by traversing the tree: concatenation joins roots and restores tree balance, slicing splits at the two bounds and leaves the middle part, reversing just as complementation flipps flags on the edges.

Reading actual slice content in BioseqDB is implemented using 
\path{lazy_sequence_view<A>} of
table~\ref{tab:sequence-representation-specializations}. It's built for the
duration of a single call and the tree operations read only metadata from sequence locators (such as lengths). This means that we don't need to fetch large relations with sequence content and slicing is very performant.
In the pipeline specific stages (like SIMD or GPU kernels) can request contiguous region of sequence and BioseqDB will materialize it into its own packed buffer first.

I implemented concatenation support for SQL text literals as well. This means that we can concatenate sequences with text directly without casting them, but this has it's own limitations:
\begin{itemize}
  \item Slicing and reversal can operate on text without no known alphabet because they need
        only positions and order.
  \item Joining a known-alphabet sequence with a text literal validates the literal
        against that alphabet, so we require to go through entire literal (which shouldn't be a problem as we don't expect very long literals as this should be done via loading FASTA first into the table)
  \item Reverse-complement requires known alphabet with a complement rule
        for every symbol in that alphabet.
  \item Two different alphabets are not converted automatically to one another and this will result in an error.
\end{itemize}
