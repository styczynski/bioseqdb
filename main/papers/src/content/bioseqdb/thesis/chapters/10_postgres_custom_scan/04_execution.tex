\subsection{Dispatch buffer internals}
\label{sec:dispatch-buffer-api}

The main component I want to discuss here is the dispatch buffer: a container abstraction reponsible for retrieving, storing, distributing and collecting of the tuples with results.
This requires managing memory and lifetime of Postgres tuples (both incoming from table and outgoing to the user).

\subsubsection{Handling tuples}

Postgres offsers \texttt{TupleTableSlot*} type, which represents reusable holder for a tuple.
The Postgres executor keeps one scan slot on the expression node and asks the table access method to fill that same holder on every fetch.

This holder consist of a tuple descriptor, current column values, null flags, and a small operations (functions pointers) table that knows how to read or copy the physical layout currently stored inside it~\parencite{postgresql17_tuptable}.
The tuple descriptor is the struct holding information about the columns schema (how many attributes it has, names of the attributes and their types with additonal metadata).

PostgreSQL offsers the following types of slots~\coderef{postgres17/src/include/executor/tuptable.h}{Builtin tuple table slot types}{TTSOpsMinimalTuple}{38}:
\begin{itemize}
  \item \textbf{Buffer heap tuple} (\texttt{TTSOpsBufferHeapTuple}).
        The slot points at a row that still lives in a shared buffer page.
  \item \textbf{Heap tuple} (\texttt{TTSOpsHeapTuple}).
        The slot owns a \texttt{palloc} copy of a full on-disk row with system columns (added by Postgres)~\parencite{postgresql17_storage_page_layout}.
  \item \textbf{Minimal tuple} (\texttt{TTSOpsMinimalTuple}).
        The slot owns a compact copy of the user columns only without system columns added by Postgres.
        Sort, hash, and materialize nodes use this type because it is smaller than a heap tuple.
  \item \textbf{Virtual tuple} (\texttt{TTSOpsVirtual}).
        Instead of storing entire row it stores arbitrary data in array (usually pointers to the actual values, so we can reference existing tuple).
\end{itemize}

The TAM has one slot that is used to return tuples and it's overwriten with each tuple fetch (\texttt{getnextslot} call). This means that dispatch buffer has to store the tuple somewhere.
In a dispatch buffer method called \texttt{submit\_scan} I allocate a fresh slot with \texttt{TTSOpsMinimalTuple}, copy the current user columns with \texttt{ExecCopySlotMinimalTuple}, 
and store it with \texttt{ExecStoreMinimalTuple}.
The third argument is \texttt{shouldFree=true}, so the copied slot owns the bytes and will \texttt{pfree} them when the buffer later drops the slot.

Sequence tuples in the dispatch buffer needs to represent lazy-loadable seqences, so during their lifetime they can become of of the 3 types (I need to distinguish them, because in code they are all just minimal tuples, but semantically express different  concepts):
\begin{itemize}
  \item \textbf{Locator}: This object is what is usually stored in the user table and represents entire sequence stored in separate internal table. This is "unhydrated" sequence.
  \item \textbf{Expanded}: Postgres has a flag \path{VARATT_IS_EXTERNAL_EXPANDED} (I call this in a code "expanded recipe") to mark the value is not a flat byte array yet, but complex structure in memory. This happens when sequence holds piece-tree (slice graph)~\ref{sec:sequence-piece-tree}, so we have multiple slice operations to perform if we want to convert this value to flat sequence. This is also different form of "unhydrated" sequence.
  \item \textbf{Varlena}: Representing "hydrated" sequence fragment, so the slices or locator were converted to some flat byte array.
\label{lst:tuple-types}
\end{itemize}
The alignment pipeline uses first two representations directly and as mentioned before when discussing sequence abstractions~\ref{sec:sequence-abstractions} the sequence will be kept as a locator or piece-tree until the actual data is requested~\ref{fig:execcustomscan-dispatch}. Then I load requested bytes and return them directly.
However in some cases we need to convert the tuple into 3rd form. If user requests slice projection directly it goes through separate branch of BioseqDB handling where that conversion is performed:

\begin{minipage}{\linewidth}
\begin{lstlisting}[style=bioseq-search-sql,caption={Direct projection of a sequence slice.},label={lst:sequence-slice-projection}]
SELECT seq[2:3] FROM table;
\end{lstlisting}
\end{minipage}

The code in \texttt{ExecCustomScan} pulls one TAM row, runs filtering conditions (these can reject the row based on metdata) and on success calls \texttt{submit\_scan} to let buffer copy the tuple.
When the copies in buffer reach the set capacity \texttt{dispatch\_batch\_capacity} \(8192 = 2^{13}\), \texttt{ready\_to\_dispatch} flag changes to true so the scan calls \texttt{run\_batch\_and\_build\_cursors}.
This method is also invoked when there are no more tuples in TAM source.

\texttt{run\_batch\_and\_build\_cursors} is where the batch starts and scanners and workers from Figure~\ref{fig:execcustomscan-dispatch} run.
It groups the locators already stored in the MinimalTuple copies, lets scanners fetch fragment bytes through the TAM under the Postgres table snapshot object and then distributes the views to workers.

Then the scan needs to read results. Reading stage calls \texttt{read\_next\_output} on every later \texttt{ExecCustomScan} to retrieve the next result (this means that in this semantic first call to \texttt{ExecCustomScan} takes very long as it needs to align first batch, while later calls return tuples one-after-another from the output cursor until they are exhausted and process repeats).
This is the place where we need to set values of nodes and project the tuple to let Postgres construct final results~\ref{sec:match-placeholder-injection}.
After Postgres consumes that projected tuple, the next call drops the previous result slot and asks for the next hit.
When the cursor is empty and the TAM source is not yet exhausted, the node calls \texttt{clear\_slots} and returns to the writing stage (this corresponds to finishing batch and starting collecting rows again)

\subsection{MVCC support}
\label{sec:scan-row-stability}

PostgreSQL holds its current input row in temporary storage called a tuple
slot, but another transaction may also update that row. \texttt{Snapshot} in Postgres is set of row versions some statement is allowed to see as it needs to perform visibility checks before doing anything~\parencite{postgresql17_mvcc}.
\texttt{configure\_params} borrows this snapshot object so later fragment reads and bulk fetches observe the same MVCC view as the original TAM fetch.
Let's see if this is compatible with the BisoeqDB model:

\begin{itemize}
  \item \textbf{Copying values:} Dispatch buffer always copies the original tuple into an owned MinimalTuple slot, so Postgres won't overwirte this data.
  \item \textbf{Saving Postgres snapshot object:} PostgreSQL uses a snapshot to
    decide which row versions a command can see. The sequence saves scan's Snapshot and checks a stored reference against the row (visibility check). Stored source fragments
    are immutable. An update publishes a new version, while an
    older snapshot can still read its earlier version. Delaying a read does
    not switch it to the latest committed sequence.\footnote{PostgreSQL 17,
    \href{https://www.postgresql.org/docs/17/transaction-iso.html}
    {Transaction Isolation}.}
  \item \textbf{Saving row numbers:} While the primary key is important for user, the row internally holds a row number that is used to indentify results.
  \item \textbf{Opening relation:} In scan I use 
    \texttt{ACCESS SHARE} relation lock to prevent conflicting operations such as dropping or
    rewriting a relation while it is in use (concurrent updates and deletes are still possible, but avoided due to snapshot mechanism)\footnote{PostgreSQL 17,
    \href{https://www.postgresql.org/docs/17/explicit-locking.html}
    {Explicit Locking}.}
\end{itemize}
I use existing Postgres mechanisms to support MVCC so it didn't require any additional custom code.

\subsection{Filter placement}
\label{sec:filter-placement}

As this mentioned here, before saving tuple into the buffer, scan checks if the filter predicate on non-alignment dependent values evaluates to true. This is done to avoid aligning rows that will be discarded anyway.
In BioseqDB there are two types of filter conditions:

\begin{itemize}
  \item \textbf{A row condition} such as \texttt{t.id > 20} depends only on
    stored columns, so is evaluated before alignment. Sometimes columns that are comparable (like Postgres primitive types) can allow min/max chunk prunning to be used.
    This is special strategy to skip entire columnar chunks with data~\ref{lst:storage-minmax-pruning}
  \item \textbf{A hit condition} This is special case of alignment prefilter. I have a separate stage in the pipeline that can be invoked to run cheaper estimation of edit distance for each sequence.
  If I detect special predicate of form   
  \texttt{bioseq.edit(t.seq) < 10} I run pipeline with prefilter enabled. This is different to the case above, because it still requires batching tuples and running pipeline, but it allows for faster termination.
  If the distance estimation yields false, then the rest of stages are skipped (there's no seeding, chaining, backtracking etc.) so we avoid even the cost of fetching the minimizers from the saved index.
  This results in great speedups, but at this time is yet an experimental feature using code from libraries that weren't developed by me.
\end{itemize}

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[style=bioseq-search-sql,caption={Filter input rows and then filter alignment hits.}]
SELECT t.id, bioseq.dp_score(t.seq) AS score
FROM targets AS t
WHERE t.id > 20
  AND mmsearch(t.seq, $1::bioseq.seq('dna5', 64))
  AND bioseq.edit(t.seq) < 10
LIMIT 5;
\end{lstlisting}
\end{minipage}

\warn{Potential features}{
  Currently I do not optimise limits so \texttt{LIMIT 5} will still evaluate all tuples in batch even after more than 5 results are found.
  I also do not provide any optimisations for score ordering, so \texttt{ORDER BY score DESC LIMIT 5} doesn't result in any specialised algorithm.
  However there are some very speicific cases that would be interesting to optimise. We can use faster chaining if we know that there's only one good hit per sequence. This isn't expressable in SQL with this API, but you can imagine providing 
  custom limit per one row: \texttt{WHERE bioseq.count(t.seq) = 1}.
