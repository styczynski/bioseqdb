\section{Dispatch buffer as glue between Postgres scan and alignment pipeline}
\label{sec:match-placeholder-injection}

I still need to explain how exactly \texttt{CustomBioseqScan} works with worker-architecture shown in Figure~\ref{fig:sequence-scan-lifecycle}.
The main abstraction here is the dispatch buffer which is reposible for transferring data between Postgres and workers.

Figure~\ref{fig:execcustomscan-dispatch} shows how Panel~(a) of Figure~\ref{fig:sequence-scan-lifecycle} looks in the context of Postgres scan.
\texttt{BioseqScan} asks for the next row from TAM. This row is placed into dispatch buffer (locator only) and dispatch buffer holds all the structures presented before~\ref{fig:sequence-scan-lifecycle} - scanners.
The dispatch buffer code then handles all view copies to the workers.

\subsection{Returning results back to Postgres}

Now I not only need to build the tuple but somehow explain to Postgres that certain values correspond to requested values of function calls like \texttt{bioseq.dp\_score(t.seq)}.
PostgreSQL evaluates output expressions through an expression tree. Before
returning its first alignment hit, the executor walks this tree and replaces the function calls with \texttt{Const} nodes. 
It writes the hit's values and null flags
into these nodes and rebuilds the output-expression evaluator so that it
reads the changed fields.
This makes Postgres know that we already computed these values. The idea was created by analyzing how ParadeDB provides its search results\coderef{paradedb/pg_search/src/postgres/customscan/basescan/mod.rs}
{ParadeDB current-result score}{exec_custom_scan}{1784}

\begin{algorithm}[htbp]
\caption{How to return tuple}
\label{alg:scan-project-hit}
\small
\begin{enumerate}
  \item Restore the original columns.
  \item For every requested BioseqDB function like \path{score(seq)}, \path{target_start(seq)}, \path{cigar(seq)} and so on, write its field from this hit into the
    corresponding typed value node.
  \item Rebuild the evaluator, then evaluate the output expressions.
  \item Return the resulting SQL row
\end{enumerate}
\end{algorithm}

\subsection{Supporting joins}

A join can lift a helper such as \texttt{bioseq.score(t.pk)} out of the scan that produced the hit and an outer join can also emit a null row when one input has no match.

The \texttt{Const} rewrite from the previous subsection is nice execution trick inside \texttt{BioseqScan}, but the join planner does not see those constants.
It still sees an ordinary function call, so PostgreSQL may copy that call onto the other input of a \texttt{LEFT JOIN}, or evaluate it again in a \texttt{Join} or \texttt{Aggregate} node.

PostgreSQL's \texttt{PlaceHolderVar} exactly to resolve this issue, however it's suprisingly low volume of documentation about it. I only found old mailing list archive, where it's described as an anti-COALESCE: the expression keeps its value on a matching row and is forced to \path{NULL} on a missing row~\autocite{lane2010_placeholdervar}.
The \texttt{PlaceHolderVar} records the relation at which the expression must be computed and the value then rises through the plan like a column.
When an outer join nulls that relation, the placeholder becomes \path{NULL} (a \texttt{Const} cannot do this as it's always the same value).
\coderef{postgres17/src/include/nodes/pathnodes.h}
  {PostgreSQL expression placement}{PlaceHolderVar}{2750}

Without that wrapper the following could happen:
\begin{itemize}
  \item The inner scan of a \texttt{LEFT JOIN} receives \texttt{bioseq.cigar(t1.pk)} even though the helper belongs to \texttt{t1} and that scan rewrites a function it does not own.
  \item A \texttt{Join} or \texttt{Aggregate} node calls the C++ stub. As I mentioned the function does not compute an alignment (the actual value is only scan-provided), so we get an error.
  \item Mishandling of \path{NULL} values:An unmatched outer-join row keeps a filled score instead of SQL \path{NULL} or \texttt{ORDER BY bioseq.score(t.pk)} after a join can sort on all-null keys.
\end{itemize}

ParadeDB uses the same mechanism for \texttt{pdb.score} and its planner function wraps the call in a \texttt{PlaceHolderVar} when the query has a join or an aggregate, so the custom scan keeps emitting the score and upper nodes do not re-run the function.
\coderef{paradedb/pg_search/src/postgres/customscan/projections.rs}
  {ParadeDB score placement}{placeholder_support}{314}

In BioSeqDB I do this using \texttt{SupportRequestSimplify} hook as \texttt{bioseq\_placeholder\_support}, where we kip placeholders when there's no joins or aggregates.
