\subsection{Designing SQL API}

A full text search interface (\texttt{pg\_search}) from ParadeDB was an important motivation for the SQL API design of BioseqDB. 
ParadeDB is an extension written in Rust that uses custom text storage engine under the hood. I deeply inspected its source code to understand how we can implement our own syntax in BioseqDB.
ParadeDB resolves similar problem as FTS can also return multiple hits for a single query.\coderef{paradedb/pg_search/src/postgres/customscan/basescan/projections/score.rs}
{ParadeDB score expression}{score_from_relation}{30}

To return custom results instead of relying on Postgres evaluating the function (We don't want to let Postgres call actual \path{bioseq.score()} function, but rether provide it ourselves. ParadeDB has similar syntax and the same problem)
 ParadeDB replaces score expressions with typed placeholders.
These placefolders are filled from the current search result before projection.
\coderef{paradedb/pg_search/src/postgres/customscan/projections.rs}
  {ParadeDB placeholder replacement}{inject_placeholders}{493}
Similar design was used in BioseqDB - described in Section~\ref{sec:match-placeholder-injection}.

\subsection{Plan lifecycle}
\label{sec:planner-support-and-ownership}
\label{sec:custom-path-plan-lifecycle}

To implement custom scan, we must understand different objects in Postgres:
\begin{enumerate}
  \item \textbf{Path:} Describes
    possible inputs, estimated work, output row count, and ordering. The
    planner compares several paths and keeps the cheapest one~\autocite{postgresql_planner_optimizer}\autocite{conway_postgres_optimizer}.
    The Genetic Query Optimizer is used only when the number of joins exceeds \texttt{geqo\_threshold}.
    A single-table \texttt{BioseqScan} is ordinary cost comparison, not GEQO.
    The path is later converted into a plan. I register my own paths so PostgreSQL knows how to access the table.
  \item \textbf{Plan:} In our case \texttt{CustomScan} contains child plans, expression trees, and descriptions of the
    search.
  \item \textbf{State:} When plan is executed, postgres creates its state via my code. \texttt{CustomScanState} holds the input cursor, alignment
    buffers for sequences and metadata, and slots for generated hit.
    Postgres will call scan repeatedly to get new rows, so I use the state to hold any information that needs to be preserved between calls.
\end{enumerate}

All types of Postgres API described in table earlier~\ref{tab:pg-scan-extension-points} mainly rely on callbacks (in Postgres called \emph{hooks}). Extension fills the structure with function pointers and let postgres know which call is handled by which function.
In this case PostgreSQL calls \texttt{PlanCustomPath} when it converts a selected custom
path into a plan and later calls \texttt{CreateCustomScanState} to create the
executor state\footnote{PostgreSQL
17, \href{https://www.postgresql.org/docs/17/custom-scan-path.html}
{Creating Custom Scan Paths} and
\href{https://www.postgresql.org/docs/17/custom-scan-plan.html}
{Creating Custom Scan Plans}.}

\texttt{ProcessUtility\_hook} is used for utility statements such as \texttt{CREATE}, \texttt{DROP}, \texttt{COPY}, and \texttt{CREATE INDEX}. This is useful to forbid user from doing certain operations (Currently I only use it to log statements).

The TAM stores the user table in columnar format: A long sequence is not kept in that table row, only a locator is stored there.
The sequence itself is stored in companion \emph{fragment sub-tables}, and all of them use the bioseq TAM as well. 
More on storage format is discussed in Chapter~\ref{sec:pg-storage-role}.
I called the process of fetching fragment from locator "hydration" and TAM is responsible for it.

BioseqDB have control over the plan using \texttt{column\_planner\_hook}.
This hook is called when PostgreSQL needs to perform planning and SQL query is already parsed. 
First BioseqDB hook validates \texttt{mmsearch} options, then it calls \texttt{standard\_planner}.
\texttt{get\_relation\_info\_hook} and \texttt{set\_rel\_pathlist\_hook} hooks, where we set options like disabling parallel scans or index-only scans and register custom access paths for cust scan, run inside that call.
Then GQO is run and finds the best path that needs to be converted into a plan, so the \texttt{PlanCustomPath} is run.
When \texttt{standard\_planner} returns we are still in the  \texttt{column\_planner\_hook}, so I'm free to rewrite plan tree freely.
The rewrite mutor performs the following changes:
\begin{itemize}
  \item \textbf{Enable vectorized execution for simple aggregates}
    Using modernized Citus/Hydra columnar vectorized optimisations I allow simple aggregates on metadta columns to be vectorized (processed in batches) for example: \path{COUNT(*)} or \path{SUM(foo_bar)}.
    If current node is Postgres \texttt{Agg} it will be replaced by custom aggregator \texttt{VectorAggNode}.
    If this plan has \texttt{VectorAggNode} as parent, then I return batches of rows instead of single tuples. Rewrite adds falgs to mark that the plan needs to change its output mode.
    Additionally Postgres \texttt{Agg}
  \item \textbf{Wrap an index scans on columnar tables}
    PostgreSQL can still choose a metadata index on a \texttt{USING bioseq} table and use external \texttt{IndexScan}.
    If that happens this index can read some tuples that shouldn't be red (columnar TAM allows removing rows. If that happens row is marked in bitmask, but index scan can go around it and still read the row, because it's physically there).
    To prevent that the \texttt{IndexScan} is replaced by custom \texttt{BioseqIndexScan} that hounours bitmask.
\end{itemize}

As entities like \texttt{bioseq.score(id)} are still ordinary functions, I discourage Postgres by using prohibitive execution costs~\footcite{postgresql17_support_functions}.
The function implementation itself mostly just emits an error, because it shouldn't be ever called.
Instead \path{ExecCustomScan} will using special Postgres expression nodes i.e \path{Const*} node to tell Postgres that the scan itself calculated the function's value and it shouldn't evaluate it by itself.
