\subsection{What the results show}
\label{sec:benchmark-interpretation}

BioseqDB was evaluated on JOIN between query and reference tables where reference table contained only one sequence and reference table contained 1024 randomly generated sequences.
The cases where divided by me into two groups:
\begin{itemize}
  \item \textbf{Index:} build the reference index first, restart PostgreSQL,
  then measure the query, including access to the stored index.
  \item \textbf{No index:} measure construction of a temporary reference index
  and the query together. The query batch shares that temporary index.
\end{itemize}

Overall the main outcomes are as follows:
\begin{enumerate}
  \item BioseqDB is the first tool to my knowing that integrates database with aligner software
  \item Memory admission system and custom grouped-MPF index allow to achieve speedups for already built index by 3x to 8x compared to minimap2 in typical cases and 100x where heavy swapping occurs for long sequences
  \item BioseqDB for preexisting index beats all common aligners and doesn't require any data preparation (other tools required customized scripts to split the long sequences into chunks)
  \item BioseqDB without index is usually slower than minimap2, but faster than other similar aligner tools (this is acceptable due to nature of the typical use cases)
  \item BisoeqDB exposed failures in terms of very inneficient GPU implementation and anomalous implementations of some of other coinfigurations (like scalar)
\end{enumerate}

\subsubsection{What an indexed minimizer comparison measures}

Scalar and SIMD-ref have similar indexed times in this example, where they
reuse the same kind of reference index and share most of the query pipeline.

\BenchmarkSlice{aws-2-k15-w10}
  {mpf-scalar-scalar-block,mpf-simdref-scalar-block}
  {index-2-k15-w10-dna4-m7a,index-2-k15-w10-dna4-m7i}
  {Two minimizer implementations with MPF, Scalar-DP and Block held fixed.}
  {tab:bench-indexed-minimizers}

\warn{An indexed row does not measure reference-index construction}{
The benchmark requires a compatible persisted \emph{reference} index. It builds
that index before restarting PostgreSQL, and does not rebuild its minimizers
inside the measured query. The query sequences themselves have no persisted
minimizer index: their minimizers are extracted to search the reference.
Changing the minimizer therefore does not measure reference construction
again, so the results above measure the same thing for the "index" case.}

In each small table, the upper duration is A: the complete query measurement,
and the lower duration is B: the A time with substracted time for recorded CIGAR/MAPQ.
This means that in BioseqDB B represents all the time excluding final alignment.
You can find complete raw result tables in Benchmark results Section~\ref{sec:benchmark-results}.

The measurements were performed on AWS machines of various classes always of size xlarge and local machine with MacOS ARM64.
The exact specifications and measurement methotolopgy can be found in the benchmark section as well.

The minimap2 baseline is always gray in the tables, while preferred configuration (grouped-MPF with all SIMD routes) is marked with yellow colour.

\subsubsection{Specialized kernel failure}
\label{sec:bench-wide-hash}

The scalar MPF configuration takes much longer on the smaller reference with
longer k-mers than on the larger reference with shorter k-mers.

\BenchmarkSlice{aws-4-k15-w10}
  {mpf-scalar-scalar-block,mpf-bounded-simd-block}
  {index-4-k15-w10-dna4-m7a,index-4-k15-w10-dna4-m7i}
  {Indexed DNA4 with the shorter k-mer profile.}
  {tab:bench-short-hash}
\BenchmarkSlice{aws-2-k20-w15}
  {mpf-scalar-scalar-block,mpf-bounded-simd-block}
  {index-2-k20-w15-dna4-m7a,index-2-k20-w15-dna4-m7i}
  {Indexed DNA4 with the longer k-mer profile, despite a smaller reference.}
  {tab:bench-wide-hash}


Smaller hashes can be directly fetched from MPF index, while for longer the directory row is used~\ref{sec:index-direct-lookup}~\ref{sec:index-control-scan-waves}, this however doesn't explain the difference.
One possible explanation is that hash for scalar is too wide and it forces these lookups, because bounded SIMD algorithm limits the width of hashes.
Alternatively this could be a problem with how the algorithm uses memory admission system and going into SWAP usage, but such drastic change is unlikely.
What I think is the most likely, is the k=15, w=10 has certain optimisations I hardcoded first. When migrating algorithms to be generic I could do it in a way that the performance is heavily deraded for non-default caase.

Nevertheless I'm still accepting these results as k=15, w=10 are the most common (and default minimap2) used parameters.

\subsubsection{Anomalous A/B difference}
\label{sec:bench-a-b}

This MPS configuration loses to minimap2 on complete time even though its
B time is lower.

\BenchmarkSlice{aws-2-k20-w15}
  {minimap2,mps-scalar-simd-block}
  {index-2-k20-w15-dna4-m7a,index-2-k20-w15-dna4-m7i}
  {An indexed comparison whose direction changes between A and B.}
  {tab:bench-a-b}

I previously had problem with implementation of divergence-sort in
Section~\ref{sec:minimizer-divergence-history} but divergence is not substracted in B.
Such big difference may be caused by either problems with measurement methodology (because alignment is massively parallel and calculating B is not correct) or most of the slowdown happens in CIGAR work
due to special treatment of N bases in DNA5.

\subsubsection{BioseqDB memory admission system}
\label{sec:bench-machine-pressure}

The minimap2 baseline itself slows sharply on C7G.

\BenchmarkSlice{aws-4-k20-w15}
  {minimap2,mpf-bounded-simd-block}
  {index-4-k20-w15-dna4-m7a,index-4-k20-w15-dna4-m7i,index-4-k20-w15-dna4-m4,index-4-k20-w15-dna4-c7g}
  {The same indexed workload across the AWS machine classes.}
  {tab:bench-machine-pressure}

The C7G minimap2 record reports severe paging during measurement.
C7G has less physical RAM than
the other AWS classes, so the index with more unique minimizers causes excessive paging.

M4 is slower in many comparisons, but is not uniformly the slowest machine.
Its older CPU and lower EBS (AWS disk) bandwidth make it slow, but in cases like presented here C7G can also undergo reduced performance~\autocite{aws_ebs_limits}
The benefit of BioseqDB is that we activelly avoid using SWAP by making sure the memory is sufficient for all allocations of commom memory arenas.

\subsubsection{Index query slower than no-index query}
\label{sec:bench-index-reversal}

\BenchmarkSlice{aws-2-k20-w15}

This means that BioseqDB requires further optimisation to enable adappitve decisioning whether to use index of not. In this case despited repeated measurements the machine could go 
period of temproarily reduced disk IOPS, which caused disk reads to be slower than computing index from scratch (in second case the pipeline doesn't have to interface with disk as much)

\subsubsection{GPU native algorithms are slower than CPU}
\label{sec:bench-gpu-performance}

Unfortunatelly BioseqDB was my first GPU implementation in Vulkan. I tested it both on local machine with integrated GPU and on remote Vast.ai rented GPU machine.
In both of the cases there were issues with allocating to much memory on GPU or using CPU host memory instead of GPU.
It's worth considering G3SA approach with different order of chaining scores computations and also consider one integerated kernel to perform all pipeline stages on GPU without frequent host-device
transfers.
