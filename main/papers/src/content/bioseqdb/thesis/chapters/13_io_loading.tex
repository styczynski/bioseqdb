\section{Ingestion is part of the database contract}
\label{sec:io-loading-contract}

The alignment kernels described in the preceding chapters begin with compact
sequences, but public biological archives normally deliver text.  A FASTA
record contains a header and one or more sequence lines. A FASTQ record adds a
separator and a quality string whose length must agree with the sequence.
Either format may be compressed, individual records may be much larger than a
PostgreSQL allocation, and a header may itself encode several typed metadata
fields.  Loading is consequently more than calling a file parser before an
\texttt{INSERT}.  It is the boundary at which byte-stream framing, alphabet
interpretation, compact storage, relational typing, and transaction semantics
must agree.

BioSeqDB treats that boundary as a pipeline with explicit contracts.  The
non-PostgreSQL I/O modules acquire and parse bytes.  They know nothing about
\texttt{Relation}, \texttt{Datum}, memory contexts, or SQL errors.  The
PostgreSQL loader selects an alphabet and storage width registered in the
compiled build from the destination column, consumes already packed chunks,
creates the out-of-line sequence source, and only then publishes the parent
row containing its locator.
Header interpretation is also divided at this seam: format recognition and
field extraction are ordinary C++ code, whereas conversion to an SQL type,
default evaluation, constraint checking, and row insertion remain PostgreSQL
operations.

In this chapter, \emph{reliable loading} has five concrete meanings:

\begin{enumerate}
    \item a finite input is framed into exactly the intended FASTA or FASTQ
    records, including multiline records and compressed input.
    \item memory use is independent of the length of the largest sequence on
    the path used by \texttt{bioseq.load}.
    \item symbols are packed directly into the alphabet and storage-unit layout
    declared by the destination \texttt{bioseq.seq} typmod.
    \item every diagnostic identifies the earliest terminal failure and, where
    possible, the record and destination column.
    \item a failed SQL call does not expose a successfully committed prefix as
    though it were a completed load.
\end{enumerate}

These requirements differ from those of a standalone mapper. Minimap2's
ordinary input route can parse a file into process-owned sequences and build an
in-memory index~\cite{minimap2_paper}. BioSeqDB must additionally preserve
relational defaults and constraints, stream sequence fragments into
database-owned relations, publish locators in a safe order, and cooperate with
PostgreSQL's transaction and resource-owner machinery.  Conversely, the
reusable BioSeqDB batch reader and standalone FASTA/FASTQ writer do not
automatically acquire database transactionality merely because the PostgreSQL
loader uses them.  Keeping those guarantees separate is a recurring theme of
the implementation.

\section{Layered reader architecture}
\label{sec:io-reader-architecture}

The small protocol at the bottom of the reader is
\texttt{bioseq.io.source\_core}.  Its \texttt{io\_source} concept requires a
\texttt{read\_into(dst,capacity)} operation returning the byte count, end-of-file
state, and error state, together with \texttt{last\_error\_message()}.  There is
no virtual base class.  Each parser instantiation is monomorphic in its source,
so a POSIX read, an mmap view, zlib, and the custom parallel gzip source share
one loop without paying a virtual call at every refill.  This lightweight
contract also lets generated external-provider clients, discussed in the next
chapter, supply bytes without importing the sequence-alphabet or PostgreSQL
graphs.

\subsection{Source selection and format selection}

\texttt{infer\_sequence\_file\_kind} is a PostgreSQL-independent table lookup.
It accepts \texttt{.fasta}, \texttt{.fa}, and \texttt{.fna} for FASTA and
\texttt{.fastq}, \texttt{.fq}, and \texttt{.fnq} for FASTQ, case
insensitively.  The optional suffixes \texttt{.gz}, \texttt{.bgz}, and
\texttt{.bgzf} are stripped before that lookup.  The resulting gzip-suffix bit
is informational. The byte source independently checks for the RFC 1952 magic
bytes \texttt{1f 8b}~\cite{rfc1952_gzip}. Thus a gzip-compressed file with a
misleading plain suffix can still be decompressed, while a plain file named
with a gzip suffix does not force decompression.

The record grammar is not inferred from file contents.  This is intentional:
the parser is instantiated once for either FASTA or FASTQ and does not branch
between grammars per record.  It also means that an incorrectly named file
produces a precise grammar error rather than being heuristically reclassified.
Compression and grammar therefore have different trust boundaries:
compression is safely magic-sniffed, but the caller is responsible for a
recognized format extension.

The PostgreSQL loader and its decompressed-prefix sampler use
\texttt{stream\_sequences\_file} and the same source-selection helper. For a
plain input this helper first attempts
\texttt{mmap\_source::\allowbreak try\_open\_\allowbreak with\_magic}. A mapped input can be presented
directly to the parser, eliminating slab refills and copies. If mapping is
unavailable or outside its configured size limit, a
\texttt{posix\_read\_source} retries \texttt{EINTR} and supplies sequential
access hints where the platform supports them. For every gzip input the SQL
loader and prefix sampler select zlib's \texttt{gzread}-based source. These
loader-selected sources strip one leading UTF-8 byte-order mark.

The general batch entry point, \texttt{read\_sequences\_file}, has a broader
dispatcher. It uses zlib below the 16 MiB compressed threshold and attempts
the custom parallel source for a larger gzip input. The custom source does not
currently strip a byte-order mark from the decompressed output. Its dispatcher
contains a construction-fallback branch, but
\texttt{parallel\_gzip\_source::try\_open\_from\_mmap} is
\texttt{noexcept}, has no implementation branch that returns
\texttt{unexpected}, and allocates with \texttt{make\_unique}. Construction
failure is therefore an intended policy, not a demonstrated operational zlib
fallback. Once decompression emits data, an error is terminal. Restarting
through zlib would duplicate the emitted prefix unless the entire consumer
state were rolled back.

\subsection{Parallel gzip and the librapidarchive experiment}

The custom parallel source belongs to the general batch reader. It is not
selected by \texttt{bioseq.load} or by the loader's header-prefix sampler. The
source maps compressed bytes and divides DEFLATE work among workers. Its
\texttt{chunk\_fetcher} owns eight reusable arena slots,
delivers chunks to the consumer in logical order, carries a 32 KiB trailing
window between dependent pieces, and rejects a chunk whose decompressed output
would exceed 256 MiB. The public option supplies a 4 MiB chunk target when no
override is configured. The 32 MiB fetcher constructor default applies only
when no caller-provided value reaches that lower layer. Automatic worker
selection reserves two hardware
threads and caps the common path at eight, while the fetcher itself enforces a
hard maximum of twelve.

This is the surviving result of several compression experiments.  An archived
design proposed direct integration with librapidarchive/rapidgzip and its
marker-based independent-block technique.  The early implementation report
showed that simply overlapping parsing with a single dependency chain could
not escape the serial DEFLATE ceiling. The current core I/O compression path
no longer depends on that library. It contains BioSeqDB-owned gzip header,
Huffman, DEFLATE, block-finding, window, and chunk modules.  The
external-provider subsystem uses libarchive separately for archive containers,
but that is not the FASTA/FASTQ gzip backend described here.  The conceptual
inheritance remains:
find independently decodable work, represent unresolved back-references when
necessary, resolve them from preceding windows, and drain results in order.

Table~\ref{tab:io-evidence} summarizes the corrected gzip experiment. DOC0181
establishes that the much larger notebook bar came from a plain-file mmap
dispatch rather than the gzip bucket, so that bar is excluded from the
evidence. The retained result did not meet the original multi-gigabyte target.

There is also a current integrity limitation. The compression tree contains a
gzip-footer parser and state fields for the expected CRC32 checksum and the
modulo-\(2^{32}\) uncompressed-size field, ISIZE. The setting
\texttt{parallel\_gzip\_verify\_crc} defaults to true. In the inspected
\texttt{parallel\_gzip\_decoder}, however, the emitted bytes only update a
running CRC before the state is reset at a member boundary.  No current path
compares that value or the observed size with the footer's expected CRC32 and
ISIZE.  The option therefore pays for checksum accumulation but does not yet
establish end-to-end footer verification. The separately selected zlib route
has zlib's normal stream validation, but the custom parallel route should not
be described as fully integrity-checking until the comparison is wired and
corrupted-member tests prove it.

\section{Incremental parsing and direct compact encoding}
\label{sec:io-parsing}

The parser never constructs a temporary ASCII sequence and then repacks it for
the database.  Its state machines append headers to byte storage and send body
spans to alphabet-specific packing kernels. A \texttt{buffer\_slab} starts at
1 MiB. If a record crosses a refill boundary, \texttt{make\_room} moves only
the unread suffix. If the unread record fills the slab, capacity grows
geometrically, with smaller increments after 8 MiB, up to the configured 1 GiB
hard limit.  This path supports general batch reading.  The PostgreSQL
streaming path drains complete packed units during a record and therefore does
not need the slab to grow to the record's full size.

\subsection{FASTA framing}

The FASTA state machine moves through header sigil, header, body, and finished
states.  It accepts CRLF and LF line endings and arbitrary body line wrapping.
For the common DNA4/\texttt{uint64\_t} case, a fused SIMD loop both finds the
next record sigil and converts body bytes into two-bit words, avoiding a
separate boundary scan over the same memory.  Other alphabets use the generic
line-oriented encoder.  At record completion, the encoder flushes its partial
storage unit and records the final padding, which is necessary to distinguish
real symbols from unused high-order slots in the final word.

\subsection{FASTQ framing}

FASTQ cannot be parsed by searching every line that begins with
\texttt{@}.  A quality line may legally begin with \texttt{@},
\texttt{+}, or \texttt{>}, and both the sequence and quality may span
multiple physical lines.  BioSeqDB therefore:

\begin{enumerate}
    \item consumes one \texttt{@}-prefixed header.
    \item accumulates sequence lines until a line beginning with
    \texttt{+}.
    \item skips the remainder of that separator line.
    \item consumes quality bytes until their newline-stripped byte count equals
    the raw sequence byte count.
\end{enumerate}

The final count is intentionally \emph{not} the number of accepted packed
letters.  A byte may be absent from the selected alphabet and be dropped by the
encoder, but it still occupies one quality position in the source file.
\texttt{fastq\_parser\_state} therefore tracks
\texttt{sequence\_byte\_count} separately from the encoder's accepted-letter
count.  A truncated quality section and a quality section that overshoots this
count are terminal data errors.  This distinction prevents alphabet
normalization from shifting the parser onto a later record boundary.

\subsection{Alphabet and storage-width dispatch}

The destination table, rather than the input filename, defines the alphabet.
\texttt{resolve\_load\_columns} requires exactly one
\texttt{bioseq.seq} column, decodes the alphabet code and byte width from its
typmod, and rejects an unparameterized sequence type. The loader then performs
one runtime-to-compile-time fan-out:

\[
  (\text{alphabet code},\ \text{storage width},\ \text{FASTA/FASTQ})
  \longrightarrow
  \texttt{stream\_sequences\_file<A,Unit,Format>}.
\]

The generic C++ templates are not the same as the compiled PostgreSQL surface.
The checked-in \texttt{BIOSEQ\_OPTTIMIZATION\_LEVEL=0} profile registers DNA4
with eight-byte storage units. Profile 1 registers DNA4 and DNA5, still with
eight-byte units. Level 2 or above registers DNA4 and DNA5 with one-, two-,
four-, and eight-byte units. Levels 3--5 change other template axes but retain
these loading layouts. The loader dispatches only across this
\texttt{pgseq\_supported\_alphabets} registry. RNA, amino-acid, and further
alphabets are architectural extension possibilities, not current SQL-loader
capabilities.

For every registered combination, packed chunks already have the column's
native layout. The PostgreSQL sink computes their byte count from the
alphabet's letters-per-unit value and appends them without a second
representation conversion. This is the ingestion counterpart of the generic
\texttt{compact\_sequence\_range} abstraction developed in the
sequence-representation chapter. Representation genericity begins before the
data reaches the table, while deployment-time registry selection determines
which instantiations are available to SQL.

The current policy for unknown symbols is permissive.  Both FASTA and FASTQ
invoke the encoder with \texttt{unknown\_byte\_policy::DROP}.  Although
\texttt{reader\_options} exposes \texttt{strict\_alphabet}, the inspected
parser does not consult it.  Thus strict FASTQ framing is implemented, but
strict alphabet rejection is not.  This should be understood as a current
data-cleaning policy, not as validation that every input symbol belongs to the
declared alphabet.

\subsection{General batches}

\texttt{read\_sequences\_file} accumulates many records into a
\texttt{sequence\_batch}.  Records share backing vectors and are addressed by
prefix offsets, avoiding one heap allocation per header, body, and quality
string.  For plain mmap inputs of at least 1 GiB, the reader may find valid
record boundaries and divide the map among at most eight parser shards.  Each
shard owns its batch storage. Handler calls are serialized where required, and
cross-shard record delivery is not guaranteed to preserve file order.  This is
acceptable for consumers whose semantics are set-like, but it is not used by
the PostgreSQL loader.

When \texttt{worker\_count} is nonzero, the general asynchronous path parses on
the caller and submits completed batches to the project-wide task pool.  Its
module comment still describes per-worker single-producer,
single-consumer (SPSC) rings, and
\texttt{concurrency\_options} still has a \texttt{ring\_capacity} field, but
the current body dispatches task-group closures directly.  The field does not
bound outstanding batches.  The thesis therefore treats the ring design as
history rather than a current guarantee.

\subsection{The PostgreSQL streaming contract}

\texttt{stream\_sequences\_file} forcibly sets the worker count to zero and the
parser count to one.  Its \texttt{run\_sync\_stream} loop emits:

\begin{verbatim}
begin_record(header)
chunk(packed_words, represented_base_count, end_of_record=false) ...
chunk(final_words, represented_base_count, end_of_record=true)
end_record()
\end{verbatim}

Only full storage units are drained mid-record.  The last chunk subtracts the
padding captured when the parser finalizes the record. The word span remains
valid for the duration of the callback, so the default sink copies it straight
into \texttt{sequence\_stream\_writer}.  If a sink implements
\texttt{chunk\_owned}, ownership can instead cross an asynchronous boundary.
This protocol is what permits a multi-gigabase FASTA record to be stored
without allocating a multi-gigabyte contiguous value.

The PostgreSQL stream sink calls \texttt{writer.begin} once per record,
\texttt{append\_packed\_bytes} for every chunk, and
\texttt{writer.finish} to obtain a \texttt{PendingSequenceSource}.  It then
builds the small parent-row locator and metadata tuple.  The call to
\texttt{publish\_after\_parent\_row} occurs only after
\texttt{BioseqColumnWriteRow} has copied that tuple.  This order links the
out-of-line sequence source and its relational locator without first
publishing a source that no parent row references.

\subsection{Optional parser/writer overlap}

The only currently explicit reader-to-writer backpressure is the optional load
overlap path.  A PG-free producer task runs the same single-parser stream and
places owned begin, chunk, and end events in a mutex/condition-variable FIFO of
capacity 16.  The PostgreSQL backend thread drains the queue and performs every
relation, memory-context, constraint, and write-state operation.  A full queue
blocks the producer.  A consumer exception closes the queue so the producer
can stop rather than deadlock. After joining, the original consumer exception
remains authoritative.

Table~\ref{tab:io-evidence} shows that the queued variants did not outperform
the direct loader in this experiment. The report later judged its earliest
direct baseline optimistic. The defensible conclusion is therefore
qualitative: queue synchronization and ownership traffic did not accelerate
the measured workload. The \texttt{bioseq.load\_overlap} setting remains
available for other source/write ratios but defaults to off.

\section{Header dialects and typed relational mapping}
\label{sec:io-header-mapping}

A FASTA header is nominally free text, but established repositories encode
structured identifiers inside it.  For example, a UniProtKB header begins with
a pipe-delimited database, accession, and entry name, followed by a description
and fields such as \texttt{OS=}, \texttt{OX=}, and \texttt{GN=}.  Treating
the whole header as one text column preserves bytes but loses the opportunity
to index accession, organism, taxonomy identifier, dates, ranges, and numeric
fields using PostgreSQL types.

BioSeqDB's parser recognizes AUTO and PLAIN modes plus UniProtKB, UniRef,
UniParc, UniMes, SPD, NCBI generic, NCBI GI, NCBI Protein Data Bank (PDB),
RefSeq, GenBank,
GISAID, and IMGT dialects.  Format definitions are constexpr tables in
\path{io/identifier_parser/identifier_formats.cppm}.  They state
whether a field is positional, free description text, a
\texttt{KEY=VALUE} tag, or a bracket tag, together with canonical names and
aliases.  Column-name comparison lowercases ASCII and removes underscores and
hyphens, so a schema can use conventional SQL spelling without teaching the
parser a second set of extraction rules.

AUTO detection is a bounded, once-per-file operation.  The loader reads at most
256 KiB of \emph{decompressed} prefix and samples at most 16 headers using the
same source-selection helper as the main stream.  FASTQ sampling follows the
logical sequence-plus-quality lengths instead of assuming four physical lines.
it therefore does not mistake an \texttt{@} in quality data for the next
header.  Known formats vote across all sampled headers, with deterministic
enum-order tie breaking.  An unstructured sample becomes PLAIN, while
unrecognized structured metadata remains in generic AUTO mode.

\subsection{Mapping is resolved once}

Before streaming records, \texttt{resolve\_identifier\_mapping} operates on a
PostgreSQL-free array of \texttt{column\_descriptor} values.  Its priority is:

\begin{enumerate}
    \item explicit user mappings from
    \texttt{bioseq.column\_mapping[]}.
    \item implicit matches between fixed-format fields and destination column
    names.
    \item selection of an identifier text column, preferring a unique primary
    key or a conventional identifier alias.
    \item generic metadata routes for AUTO.
    \item a decision whether mapped metadata should be stripped from the
    identifier value.
\end{enumerate}

The result is a compact routing table from positions or normalized keys to
destination slots.  Per-record parsing performs one SIMD-assisted scan for
\texttt{|}, \texttt{=}, \texttt{[}, and \texttt{]}, stores common delimiter
tokens in an inline small-vector, and reuses parse scratch across records.
The parser writes raw byte ranges through the
\texttt{is\_identifier\_dest\_writer} concept.  A small type-erased
\texttt{identifier\_writer\_ref} prevents every header extractor from being
instantiated again for every alphabet, storage width, and file format.

The database implementation, \texttt{pg\_identifier\_writer}, caches each
destination type's input function and typmod. Plain unconstrained text can use
a direct text construction. Constrained character types and arbitrary scalar,
range, or multirange types use \texttt{OidInputFunctionCall}.  A convenient
\texttt{lo..hi} header value is rewritten to PostgreSQL's inclusive range
syntax before the type input function is invoked.  Date and timestamp
interpretation consequently follows the session's PostgreSQL
\texttt{DateStyle}, just as it does for other SQL input.

Unmapped defaults are compiled as executor expressions once per load and
evaluated per row.  Volatile defaults are therefore not accidentally frozen at
load start.  The completed virtual tuple passes through
\texttt{ExecConstraints} before the columnar row write.  Per-tuple expression
and write memory contexts are reset only after by-reference datums have been
copied. This ordering preserves five PostgreSQL obligations:

\begin{enumerate}
    \item metadata columns are claimed before identifier-column selection.
    \item AUTO sampling precedes mapping.
    \item multiline FASTQ framing remains valid.
    \item direct column-store writes enforce relation constraints.
    \item per-row memory is reset instead of accumulating until end of file.
\end{enumerate}

Table~\ref{tab:io-evidence} reports the header-parser microbenchmark. The
structured path includes six-field extraction and routing, but the measurement
is not an end-to-end SQL throughput result.

\section{SQL integration, failure propagation, and transaction semantics}
\label{sec:io-sql}

The generated SQL surface is conceptually:

\begin{verbatim}
bioseq.load(
    target_table  regclass,
    file_path     text,
    header_format text DEFAULT 'auto',
    columns       bioseq.column_mapping[] DEFAULT NULL
) RETURNS bigint
\end{verbatim}

The return value is the number of loaded records.  Existing two-argument calls
remain valid through defaults.  The target relation is opened with
\texttt{RowExclusiveLock}.  Schema discovery rejects zero or multiple sequence
columns, identity/generated destinations, ambiguous or unknown mappings, and
an unmapped \texttt{NOT NULL} column without a default before the first record
is written.

The steady-state algorithm can be expressed as follows:

\begin{verbatim}
kind      = infer FASTA/FASTQ from extension
columns   = inspect target and decode alphabet and storage width
format    = sample headers if AUTO
routing   = resolve typed destinations once
dispatch  = instantiate <alphabet, unit-width, record-format> once

for each streamed record:
    sequence_writer.begin()
    for each bounded packed chunk:
        sequence_writer.append_packed_bytes(chunk)
    pending_source = sequence_writer.finish()

    tuple = all NULL
    tuple.seq = locator(pending_source)
    parse header and route raw fields into cached PostgreSQL input functions
    evaluate still-unset defaults
    enforce relation constraints
    write parent tuple
    pending_source.publish_after_parent_row()

flush parent write state and every fragment-shard write state
advance command counter
optionally build configured sequence indexes in one post-load pass
return record count
\end{verbatim}

\subsection{Error domains}

Non-PostgreSQL operations use \texttt{std::expected} or C++ exceptions carrying
owned strings.  The PostgreSQL boundary maps them to an SQLSTATE and raises an
ERROR through a checked C++ seam.  The reader captures only the first terminal
diagnostic. Later cleanup must not hide it. PostgreSQL type input, default, or
constraint errors retain their native message and receive an
\texttt{ErrorContextCallback} suffix containing the record number, optional
column name, and at most 240 bytes of the header.  The bound prevents a corrupt
giant header from producing an unbounded error message.

Cleanup is explicit even though the surrounding transaction remains the final
atomicity authority.  The loader tears down its executor, slot, relation, and
write-state resources at the appropriate boundary. Successful execution
flushes both parent and fragment write states, performs
\texttt{CommandCounterIncrement}, and only then permits an optional index scan
to observe the new locator-backed rows.  If an exception escapes,
PostgreSQL aborts the statement's transaction scope, so partial rows are not a
separately committed successful prefix.  A caller that invokes
\texttt{bioseq.load} inside a larger explicit transaction retains the usual
PostgreSQL choice to roll back the transaction or recover at a savepoint.

This is stronger than ``delete the output file on parser error''. Sequence
data spans fragment relations and a parent column-store row. PostgreSQL's
write states, resource owners, locks, snapshots, command visibility, and WAL
semantics are the mechanisms that define visibility and rollback.  The loader
therefore avoids inventing a second transaction protocol inside the I/O module.

\section{The standalone writer is a different contract}
\label{sec:io-writer}

The I/O module also exports a FASTA/FASTQ \texttt{sequence\_writer}.  It is
useful for corpus generation, benchmark round trips, and exporting compact
sequences, but it is not the implementation of PostgreSQL atomicity.
Each producer thread owns a 64 MiB output buffer by default.  At a flush point
the sink reserves a disjoint file range through an atomic
\texttt{fetch\_add}. The \texttt{pwrite} call then fills that range. Before
starting a new record, the writer flushes a threshold-crossing buffer so chunks
from different threads cannot splice a header from one record onto the body of
another.  Concurrent producers may nevertheless change record order.

The default \texttt{posix\_pwrite\_sink} opens with
\texttt{O\_TRUNC}, retries interrupted writes, and reports the first failure.
An optional mmap sink requires an upper-bound size hint and truncates the file
to the number of reserved bytes on close.  A bounded streamed-record method
decodes compact words into ASCII slices rather than materializing a
multi-gigabase body. This method may flush in the middle of one record, so it
is safe only at a quiescent single-producer point. Concurrent producer
reservations could otherwise interleave record slices. The regular concurrent
\texttt{write\_record} path keeps a whole record in a growable buffer to
preserve record atomicity, so it does not provide the same record-size bound.
FASTA defaults to no line wrapping for throughput.
FASTQ quality-length checking is configurable. In its permissive mode the
writer truncates an overlong quality or pads a short one with Phred-zero
\texttt{!} bytes.

Two limitations matter when interpreting the word ``reliable''. First, the
standalone writer deliberately omits \texttt{fsync}. Successful close means the
kernel accepted and closed the file, not that stable storage has acknowledged
it.  The mmap close path similarly unmaps and truncates but does not call the
\texttt{msync} named in its stale comment.  Second, opening truncates an
existing file immediately and an error can leave a valid prefix or partial
file.  There is no temporary-file-and-rename transaction.  Callers that require
durable atomic replacement must add that policy outside
\texttt{sequence\_writer}.  None of these limitations weakens
\texttt{bioseq.load}, whose sink is PostgreSQL storage rather than this file
writer.

Table~\ref{tab:io-evidence} reports the archived writer throughput. On the
measured Apple-Silicon host, buffered \texttt{pwrite} configurations
substantially exceeded the byte-oriented \texttt{std::ofstream} comparator.
The mmap sink was not retained because it regressed both tested cells. These
page-cache measurements omitted \texttt{fsync} and therefore do not measure
durability.

The development sequence behind these results is itself informative:

\begin{enumerate}
    \item The first reader established an \texttt{io\_source} abstraction,
    incremental FSMs, a recyclable slab, and shared batch storage.
    \item mmap direct parsing and large-file record-boundary sharding removed
    copies and exposed parallel parsing where file size amortized shard setup.
    \item The writer introduced per-thread chunks and disjoint
    \texttt{pwrite} ranges, then retained pwrite after mmap output regressed on
    the measured host.
    \item gzip work progressed from zlib and overlap experiments toward the
    current BioSeqDB-owned block/chunk decoder. The originally specified
    external rapidgzip integration was not retained.
    \item Database integration replaced whole-record batches with the
    storage-unit-parametric stream, so \texttt{bioseq.load} could ingest
    sequences beyond PostgreSQL's ordinary allocation limit.
    \item Typed header parsing was placed outside the alphabet/file-format
    template cross product and reviewed against defaults, constraints,
    multiline FASTQ, memory-context lifetime, and error context.
    \item A bounded producer/consumer queue tested parsing/write overlap.  Its
    measured regression led to a conservative default-off policy instead of
    making parallelism an article of faith.
\end{enumerate}

The current implementation is therefore not simply the fastest intermediate
prototype. It selects the paths whose guarantees compose at the SQL boundary:
single-backend database writes, bounded packed streaming, deterministic mapping
setup, explicit publication order, and PostgreSQL-managed rollback. At the
same time, the evidence boundary must remain explicit. In the source snapshot
reviewed on 28 July 2026, the
\path{bioseq/io/io_test.cpp} unit suite exercises small FASTQ records,
multiline quality framing, and an ordinary zlib gzip round trip. The
PostgreSQL \path{bioseq/integration_tests/test_load.cpp} suite is FASTA-centric
and does not currently prove a FASTQ or gzip
\texttt{bioseq.load} end-to-end case. Custom parallel-gzip comparisons are
hidden diagnostics that require an external corpus.

The implementation boundaries stated above do not alter the central
SQL-loading contract. They concern format discovery, strict-symbol policy,
optional parallel-gzip integrity and construction behavior, generic
asynchronous backpressure, and missing SQL FASTQ/gzip integration coverage.
Each can be addressed locally without changing locator publication or
transaction semantics.

\section{Conclusion}

BioSeqDB's ingestion path turns a textual archive record into two coordinated
database objects: compact sequence fragments and a typed parent row carrying
their locator. It does so without assembling a whole large sequence, without
letting worker threads enter PostgreSQL, and while dispatching through a
compile-time registry of supported layouts. The reader's reusable concepts
isolate byte sources, incremental grammars, and compact packing. The identifier
parser isolates repository dialects from SQL type conversion. The loader binds
both to PostgreSQL locks, write states, constraints, visibility, and rollback.

The intermediate results explain the final design. Mmap and fused packing
were retained because they removed data movement. Parallel gzip was retained
as a distinct general batch-reader backend and is not presented as having met
its original multi-gigabyte target. Mmap output and parser/writer overlap
remained optional after measurement showed regressions. The bounded streaming
API replaced a batch-only database path because correctness on a
multi-gigabase record matters more than an attractive small-record abstraction.
Reliable loading here is therefore not one defensive check. It is the
composition of bounded state, precise framing, generic representation, typed
relational materialization, and transactional publication.

remote-provider streams while preserving PostgreSQL thread ownership.
