\section{Range minimum query chaining}
\label{sec:chaining-rmq-idea}

The chaining score model is described in Section~\ref{sec:chaining-score-model} gives an ability to better express relationships between anchors we want to optimize. 
However it's more complex to calculate than simple linear scoring model.
As noted in equation~\ref{eq:global-score-definition-chaining-rmq}, we can compute $\text{GlobalScore}(i)$ independently for each anchor author of minimap2 did in minigraph paper~\cite{minimap2_rmq_scoring_minigraph}.
The problem then is reduced to finding the maximum among all values in continous segment of anchors.

Range minimum query~\cite{cp_algorithms_rmq} (RMQ) algorithm is used to calculate the linear score $h(j)$ for anchor, while minimap2 later calculates actual score $f_j+E(j,i)$ (and if the RMQ result is not sufficiently "good", then it tries again with different parameters)
\begin{equation}
  h(j)=f_j+\frac{\lambda_g}{2}(r_j+q_j).
\label{eq:chaining-rmq-h}
\end{equation}

\subsection{Minimap2 RMQ}
\label{sec:chaining-minimap2-rmq}

I didn't initially found papers going into details of minimap2 RMQ's implementation, so here I present detailed description of the algorithm. The minigraph paper~\cite{minimap2_rmq_scoring_minigraph} describes only the high-level approach, without going into details of the implementation.
Minimap2's RMQ is implemented using two AVL trees~\cite{cp_algorithms_segment_tree}. First of them is used to query anchors in the interval \(0<r_i-r_j\leq D\). Each time minimap2 removes nodes from the tree if either they go outside of this interval or node count reaches $C$ (the total limit of nodes per tree).
The second tree has the same structure, but is used to query anchors in the interval \(0<r_i-r_j\leq D_{\mathrm{in}}\) with the intent to have $D_{\mathrm{in}} \leq D$ so if we get an anchor candidate that is not sufficiently "good", we can then perform another query on second tree, where we will get scores for smaller neighbourhood of an anchor.
I will call this second lookup the "local scan".
Minimap2 $D_{\mathrm{in}}$ can be set to $0$ to disable second AVL tree entirely.

While the original anchor array is sorted by increasing reference coordinates $r_i$, the AVL trees order the node primarily by increasing query coordinate, then by increasing anchor index in the array (pairs $(q_j, j)$).
As we want to prevent chaining anchors with the same reference coordinate, we will not add single anchor to the trees (a "reference group" is the continous sequence in the anchor array that has the same reference position, but different query positions).
We will add entire reference group to the tree at once. This is implemented via $\Call{InsertCompletedReferenceGroup}{\(T,a,f,i\)}$ pseudocode function which checks if current anchor reference coordinate is different to the saved one.

The trees also need to remove anchors that go outside reference coordinates i.e \(0<r_i-r_j\leq D_{\mathrm{in}}, D\). This is implemented via $\Call{RemoveExpiredEntries}{\(T,a,i,D,C\)}$ pseudocode function. Such operation could be implemented by visiting each node in the entire tree, however internally minimap2 saves
pointer (cursor) to the first anchor in the window and moves it when going to next anchor. This results in better reemoval theoretical complexity. 

The last complex operation is local scan. After best candidate $j^{*}$ is selected from the main tree $T$, we calculate it's score \(c_{j^\star}=f_{j^\star}+E(j^\star,i)\) and accept it only when the anchor is "exact":
\begin{equation}
  \delta(j^\star,i)=0
  \quad\land\quad
  g(j^\star,i)\leq\ell_{j^\star}.
  \label{eq:chaining-rmq-exact}
\end{equation}
meaning that two anchors advcance equally and no more than k-mer span (as discussed earlier $k = \ell_{j^\star}$ for HPC disabled~\ref{info:minimap-hpc}). 
If that's not the case, then minimap2 runs the local scan. The scan goes through all anchors in the query coordinate interval $q_i-D_{\mathrm{in}}\leq q_j\leq q_i-1$.
This is implemented by first finding the first anchor in the tree with largest $q_i$ value that is strictly less than $q_j$ and then iterating candidates in decreasing order of $q_j$ value (this is ordinary tree traversal).
The scan itself is implemented via $\Call{ScanLocalInterval}{\(T_{\mathrm{in}},i,D_{\mathrm{in}},B,S,f,p,t\)}$ pseudocode function and is very similar to forward chaining loop in minimap2 scalar algorithm~\ref{alg:chaining-b1}. The only difference is that in the forward chaining loop without RMQ
minimap2 iteration was driven by $max\_iter$ limit for anchors not sorted by query coordinate, while in the RMQ scan we don't have $max\_iter$ limit (the minimap2 skip counter is used in the same way - it stops iteration on anchors that don't improve score several times in a row).

\info{Theoretical complexity}{
  In the previous forward chaining loop~\ref{alg:chaining-b1} we iterated over all anchors and bounded the number of iterations by $max\_iter$ limit. In the simplest calcualtion we can say that number of candidates is bounded by $\Theta(n)$ for one anchor, so entire pass does $\Theta(n^2)$ work.
  In case of RMQ each insertion and deletion (inserting reference groups and removing expired anchors) is amortized to $O(\log n)$ work for each anchor (each anchor can be added and removed at most once), so if the number of the candidates is the same, then overall work is bounded by $\Theta(n \log n + n^2)$.
  The RMQ is also inherently less friendlier to efficient pipelining and cache locality as we will need to jump across the tree frequently and it uses linear scoring model which can be less accurate. The benefit comes from the fact that RMQ can be more efficient with larger boundary limits, so it can be used for cases of long sequences with large insertions/deletions with lots of noise.~\cite{minimap2_rmq_scoring_minigraph}
}

Algorithm~\ref{alg:chaining-minimap2-rmq} shows how RMQ forward chaining is implemented inside minimap2.
\textsc{RangeBest} function returns the anchor with the largest \(h(j)\) in the
interval, or \(\bot\) if the interval contains no retained anchor, while \textsc{CompleteLink} function calculates \(E(j,i)\) from
Equations~\ref{eq:chaining-link-score}--\ref{eq:chaining-penalty}, together
with \(\delta\) and the exact (local scan) condition in
Equation~\ref{eq:chaining-rmq-exact}.

\begin{algorithm}[H]
\caption{Minimap2 RMQ forward chaining}
\label{alg:chaining-minimap2-rmq}
\footnotesize
\begin{algorithmic}[1]
  \Require sorted anchors \(a_0,\ldots,a_{n-1}\), distance \(D\),
    inner distance \(D_{\mathrm{in}}\), bandwidth \(B\), tree cap \(C\),
    skip limit \(S\)
  \Ensure scores \(f\) and predecessor indices \(p\)
  \Function{Minimap2RMQForward}{\(a,D,D_{\mathrm{in}},B,C,S\)}
    \State \(D\gets\max(D,B),\quad
      D_{\mathrm{in}}\gets\min(D,\max(0,D_{\mathrm{in}}))\)
    \State \(T\gets\varnothing,\quad T_{\mathrm{in}}\gets\varnothing\)
          \Comment{augmented AVL trees}
    \State \(t\gets(0,\ldots,0)\)
          \Comment{B1 marks for the optional local scan}
    \For{\(i\gets0\) \textbf{to} \(n-1\)}
      \State \Call{InsertCompletedReferenceGroup}{\(T,a,f,i\)}
      \If{\(D_{\mathrm{in}}>0\)}
        \State \Call{InsertCompletedReferenceGroup}{\(T_{\mathrm{in}},a,f,i\)}
      \EndIf
      \State \Call{RemoveExpiredEntries}{\(T,a,i,D,C\)}
      \If{\(D_{\mathrm{in}}>0\)}
        \State \Call{RemoveExpiredEntries}{\(T_{\mathrm{in}},a,i,D_{\mathrm{in}},C\)}
      \EndIf
      \State \(f_i\gets\ell_i,\quad p_i\gets-1\)
      \State \(j^\star\gets
        \Call{RangeBest}{T,(q_i-D,\mathrm{INT32\_MAX}),(q_i,0)}\)
      \If{\(j^\star\neq\bot\)}
        \State \((e,\delta,\mathrm{exact})\gets
          \Call{CompleteLink}{j^\star,i}\)
              \Comment{\(e=E(j^\star,i)\)}
        \If{\(\delta\leq B\land f_{j^\star}+e>f_i\)}
          \State \(f_i\gets f_{j^\star}+e,\quad p_i\gets j^\star\)
        \EndIf
        \If{\(\neg\mathrm{exact}\land T_{\mathrm{in}}\neq\varnothing
             \land q_i>0\)}
          \State \((f_i,p_i)\gets
            \Call{ScanLocalInterval}{T_{\mathrm{in}},i,D_{\mathrm{in}},B,S,f,p,t}\)
              \Comment{Algorithm~\ref{alg:chaining-rmq-local-scan}}
        \EndIf
      \EndIf
    \EndFor
    \State \Return \(f,p\)
  \EndFunction
\end{algorithmic}
\end{algorithm}

Algorithm~\ref{alg:chaining-rmq-local-scan} shows how local scan is implemented.
I didn't want to show other tree maintenance operations as there aren't many valuable details to discuss (this is usual AVL tree maintenance).

Similarily to minimap2 forward chaining we use $t_j$ array to mark visited candidates i.e  mark \(t_j=i\) means that a candidate already tested for target \(i\)
points to \(j\) through its saved predecessor. It must be noted that the for loop in the local scan algorithm~\ref{alg:chaining-rmq-local-scan} utilises the fact that anchors are sorted by query coordinate so we can just go to the leftmost node in the interval and iterate each leaf from left to right (I'm reiterating this to showcase that the for loop hides this complexity in hte pseudocode).

\begin{algorithm}[H]
\caption{Minimap2 local scan after the primary RMQ query}
\label{alg:chaining-rmq-local-scan}
\footnotesize
\begin{algorithmic}[1]
  \Require maintained inner tree \(T_{\mathrm{in}}\), target \(i\),
    local limit \(D_{\mathrm{in}}\), bandwidth \(B\), skip limit \(S\)
  \Require completed earlier scores and predecessors \(f,p\), marks \(t\),
    and current result \((f_i,p_i)\)
  \Ensure updated \((f_i,p_i)\) and marks \(t\)
  \Function{ScanLocalInterval}{\(T_{\mathrm{in}},i,D_{\mathrm{in}},B,S,f,p,t\)}
    \State \(s\gets0\)
    \For{retained \(j\in T_{\mathrm{in}}\) with
      \(q_i-D_{\mathrm{in}}\leq q_j\leq q_i-1\), by decreasing \((q_j,j)\)}
      \State \(c\gets f_j+E(j,i),\quad
        \delta\gets|d_r(j,i)-d_q(j,i)|\)
      \If{\(\delta\leq B\)}
        \If{\(c>f_i\)}
          \State \(f_i\gets c,\quad p_i\gets j,\quad s\gets\max(0,s-1)\)
        \ElsIf{\(t_j=i\)}
          \State \(s\gets s+1\)
          \If{\(s>S\)}
            \State \textbf{break}
          \EndIf
        \EndIf
        \If{\(p_j\geq0\)}
          \State \(t_{p_j}\gets i\)
        \EndIf
      \EndIf
    \EndFor
    \State \Return \((f_i,p_i)\)
  \EndFunction
\end{algorithmic}
\end{algorithm}


\subsection{RMQ re-chaining in the pipeline}
\label{sec:chaining-rmq-rechaining}

Normally Minimaps2 disables RMQ for chaining by default, the manual recommends\texttt{--rmq} for alignment through
long insertions and deletions~\cite{minimap2_rmq_manual}, but at the same time RMQ is cheaper so minimap2 can use it to perform "re-chaining". 

\info{RMQ re-chaining}{
  \emph{RMQ re-chaining} means running chaining again with a larger bandwidth to try to connect chains across long gaps.
  This is optional step that runs in minimap2 after the forward chaining and chaining backtracking - after step 3~\ref{list:chaining-components}.
  Minimap2 uses array $A$ which is sorted by radix sort by reference coordinates again and provided to RMQ chaining algorithm. Please note that this means that minimap2 does some duplicate work - first it groups anchors by the chain they belong to (placing them in $A$ array), but rechaining sorts anchors again.
  Minimap2 also discards $f$ and $p$ arrays from first chaining step.
  RMQ re-chaining will then work on the subset of original input anchors from seeding (not every anchor will form a chain that will be accepted by its length and score limits~\ref{alg:chaining-minimap2-backtrack}).
  As RMQ re-chaining is special case not enabled by default in minimap2, it wasn't in scope of this thesis - I didn't measure how many anchors are retained and how RMQ re-chaining affects quality of alignments and performance.
}

\warn{BioseqDB does not support re-chaining}{
  I don't provide any specialized stage in pipeline for re-chaining. Some of the software in literature support increasingly precise queries to improve alignments iteratively\cite{mmseqs2_gpu_paper}.
  This can be implemented in the future.
}

Normally in minimap2 RMQ re-chaining will be only enabled iff all conditions are satisfied:
\begin{itemize}
  \item RMQ re-chaining is enabled only for specific presets (assembly presets), so user have to select specific preset or use \texttt{--rmq} flag explicitly
  \item There's more than one chain (easy to satisfy)
  \item There's only 1 query in the mapping call
  \item Either query length minus span of first chain is greater than 1000 bases or span of first chain is greater than 10\% of query length (very long insertions and deletions)
\end{itemize}
The conditions above were created by me after inspection of source code, so the list might not be complete, but it illustrates why re-chaining wasn't first priority for me.

\warn{Other algorithmic limitations}{
There are some other limitations:
\begin{itemize}
  \item Including \(q_j=q_i\) allows a link with no query advance. BioseqDB
    searches from \((q_i-D,\mathrm{INT64\_MIN})\) to
    \((q_i,\mathrm{INT64\_MAX})\), so every anchor at either query
    boundary is eligible for selection (it should have minor impact on performance)
  \item Omitting the bandwidth reject i.e \(\delta>B\) allows a link farther from the
    diagonal than the configured \(B\) (this was ommited due to simpler code and RMQ having lesser priority than oder algorithms)
\end{itemize}
I didn't measure effects of these limtations neither on performance nor on quality of alignments.
}

\info{Future work}{
  The backtracking for RMQ can be removed and I could use SIMD backtracking. This would require separating forward/backward chaining into separate pipeline stages. Moreover in the future I can use specialized GPU acceleartion for RMQ (as noted before G3SA contains kernels for RMQ which weren't used).
  There exists some liteature~\cite{gpu_rmq_kreis_2026} discussing GPU acceleration for RMQ problems using ray tracing and CUDA cores (one limitation is that in the paper the RMQ base array is static, so it would require additional design work to design GPU-friendly algorithm).
}
