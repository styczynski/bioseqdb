\subsection{Why grouped MPF has a reader file}
\label{sec:index-mpf5-sidecar}
\label{sec:index-formats}

The reader file lets BioseqDB's CPU workers read a stored minimizer index
without asking the PostgreSQL backend thread to fetch each index chunk.
It is an experimental part of the batch-join implementation. There is a
public SQL path to it, but an ordinary single-table \texttt{mmsearch} query
does not use it. To explain the problem it addresses, consider this join:

\begin{lstlisting}[style=bioseq-index-sql,
  caption={Search every query sequence against stored reference sequences.},
  label={lst:index-reader-join-motivation}]
SELECT r.id AS reference_id, q.id AS query_id
FROM refs AS r JOIN queries AS q
  ON mmsearch(r.seq, q.seq);
\end{lstlisting}

Here \texttt{r.seq} is the target and \texttt{q.seq} is the query sequence.
An eligible \texttt{BioseqBatchJoin} retains the query rows, prepares one
target, searches the queries against it, and then moves to the next target.
A target may have many fragments, each with index chunks in heap rows.
Saving those chunks avoids computing the target minimizers again. However,
reading them through PostgreSQL still requires tuple access and extraction
of the \texttt{bytea} values. BioseqDB's CPU worker threads cannot perform
that PostgreSQL work themselves. The backend must supply the bytes before
those workers can use them.

The reader file moves this work to index construction. The builder copies
the index payloads from the heap rows into consecutive file ranges. A later
query opens that file with \texttt{mmap}, which gives the process an address
range backed by the file. Workers can then read the immutable arrays through
ordinary memory accesses. They do not fetch heap tuples for every index
chunk or reconstruct a complete private copy of the saved index.
This concerns access to the minimizer index. The join still reads its input
tables and fetches sequence symbols when alignment needs them.

Listing~\ref{lst:index-reader-join-motivation} explains the workload, but
its default read policy does not select the mapped CPU reader. That branch
currently requires an explicit request for a compatible stored index.
Section~\ref{sec:index-read-policy} explains this policy, and
Listing~\ref{lst:index-mapped-user-path} adds the request to the same join.
The target must also be a complete stored sequence with a compatible index
generation. Sliced or transformed targets do not meet that requirement.
Requiring an index on an unsupported query shape produces an error.

Figure~\ref{fig:index-join-read-paths} shows what changes in target
preparation. Ordinary MPF readers load stored fragment indexes and assemble
a lookup for the hashes needed by the queries. The grouped reader uses the
arrays in its file. Both reuse the prepared target across query batches.
If the executor does not use a stored index, it instead computes a temporary
lookup from the target sequence.

\subsubsection{Build the relation and file together}

The extra file introduces a consistency problem. BioseqDB now stores index
bytes in both a relation and a file. I handle this by publishing complete
\emph{generations}, rather than modifying a file while queries read it.
One generation describes one stored sequence version and one minimizer
profile. The profile identifies the algorithm, its parameters and the
representation of the saved minimizers.

For grouped MPF, an explicit \texttt{bioseq.update\_index} call performs
these steps for each sequence:
\begin{enumerate}
  \item Compute the minimizers and write the new generation's index rows.
  \item Read those rows back in index order and validate their contents.
    Copy their payload bytes into a private construction file. Copying the
    payload does not copy heap-page headers or recompute the minimizers.
  \item Add the directory and generation metadata. Where the hash domain
    supports it, also build the direct lookup described below.
  \item Finish and validate the file. Make it read-only, synchronize it and
    install a unique final name without replacing another generation's file.
  \item Record that file's identity and replace the active-generation record
    in the same database transaction. Other transactions can select the new
    generation after commit.
\end{enumerate}
The relation remains in the database. Thus this approach pays for a second
copy of the index bytes and a full reread during construction. In exchange,
later readers can open the prepared file. A query does not repeat the export.

Algorithm~\ref{alg:index-image-lifecycle} shows the construction and read
operations separately. Here $s$ is the complete stored target sequence,
$R_g$ is its index relation data for generation $g$, and $\sigma$ is the
query snapshot. The procedure names are pseudocode.

\begin{algorithm}[htbp]
\caption{Publish a complete MPF generation, then open its reader file.}
\label{alg:index-image-lifecycle}
\small
\begin{algorithmic}[1]
  \Procedure{BuildMappedMPF}{$s$}
    \State $g\gets$ a new generation number
    \State $R_g\gets\Call{BuildAndStoreMPF}{s,g}$
    \State $F\gets\Call{CreatePrivateFile}{}$
    \ForAll{payload chunks $c$ of $R_g$, in stored index order}
      \State \Call{CheckChunk}{$c$}
      \State \Call{AppendPayload}{$F,c$}
    \EndFor
    \State \Call{AddDirectoryAndMetadata}{$F,R_g$}
    \If{the hash domain supports direct lookup}
      \State \Call{AddDirectLookup}{$F,R_g$}
    \EndIf
    \State $F_g\gets\Call{CheckAndPublishReadOnlyFile}{F,g}$
    \State \Call{UpdateDescriptorAndActiveGeneration}{$s,g,F_g$}
    \State \Return $g$ \Comment{the caller commits the transaction}
  \EndProcedure
  \Statex
  \Procedure{OpenMappedMPF}{$s,\sigma$}
    \State $D\gets\Call{ReadAndCheckVisibleDescriptor}{s,\sigma}$
    \State $F_g\gets\Call{OpenAndCheckFileReadOnly}{D}$
    \State $M\gets\Call{MapFileReadOnly}{F_g}$
    \State \Call{CheckRequiredHeadersAndRanges}{$M,D$}
    \State \Return a reader whose session keeps $M$ and $F_g$ open
  \EndProcedure
\end{algorithmic}
\end{algorithm}

\subsubsection{What the reader finds in the file}
\label{sec:index-direct-lookup}

The file contains the grouped fragment arrays already described in
Figure~\ref{fig:index-mpf-mps}, together with the metadata needed to locate
them. A worker can search the fragment controls and then read the selected
positions. This is the \texttt{control\_block\_scan} route.

For supported 32-bit hash domains, the writer also adds a sequence-wide
hash lookup. It combines equal hashes from the target's fragments, so the
reader does not have to search every fragment for the same hash. This is
the \texttt{direct\_compact\_hash\_lookup} route. It contains:
\begin{itemize}
  \item \textbf{Membership bits.} Bit $B[h]$ is one when hash $h$ has a saved
    position list. The hash itself is the bit address.
  \item \textbf{List records.} Records follow increasing hash order. The
    number of set bits before $h$, called its \emph{rank}, gives the record
    number. A saved count at each 256-hash boundary avoids counting from the
    start of the bitmap. Each record gives a list start, its total count and
    the number of strand-zero positions.
  \item \textbf{Positions.} The list start is an entry number in a shared
    position array. Strand-zero positions precede strand-one positions, and
    each encoded position includes its strand bit. A single 32-bit position
    can be stored directly in its list record.
\end{itemize}

In Figure~\ref{fig:index-control-data-plane}, one set bit precedes hash 5.
Its record number is therefore 1. Record 1 gives start 2 and count 2, which
selects entries $[2,4)$ containing positions 40 and 230.

An unset bit can mean that the hash is absent or that its sequence-wide
occurrence count exceeds the saved limit, currently 65,534. The original
fragment payload remains in the file. A direct-lookup query can use a lower
positive occurrence limit, but cannot recover a list omitted at construction
by asking for a higher limit.

Direct addressing has a substantial space cost. With the minimap2 integer
hash and $k=15$, the bitmap covers $2^{30}$ hashes and occupies 128~MiB.
The saved rank counts occupy another 16~MiB. The current default bounded
ntHash profile uses a 32-bit hash domain, giving 512~MiB and 64~MiB instead.
Both figures exclude list records and positions. The writer builds this
section for supported domains even if a later query chooses fragment
controls. Wider hashes use the fragment controls without this section.

\subsubsection{Requesting the mapped reader from SQL}
\label{sec:index-example-settings}

Listing~\ref{lst:index-mapped-user-path} assumes committed
\texttt{refs(id,seq)} and \texttt{queries(id,seq)} tables using the
\texttt{bioseq} table access method. Their sequence columns have type
\texttt{bioseq.seq('dna4',32)}. The target table starts without an older
ordinary MPF relation. The example uses the current defaults listed in
Section~\ref{sec:index-runtime-selection}, including grouped construction
and disabled insertion maintenance.

The default minimizer algorithm, $k=15$ and $w=10$ are sufficient and need
no extra \texttt{SET} statements. Construction uses the configured profile
when it is present in the compiled profile registry. A later query must
match it.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[style=bioseq-index-sql,
  caption={Build grouped MPF and request its persisted CPU reader.},
  label={lst:index-mapped-user-path}]
SELECT bioseq.update_index('refs'::regclass,
                          'minimizers_per_fragment');

SELECT r.id AS reference_id, q.id AS query_id
FROM refs AS r JOIN queries AS q
  ON mmsearch(r.seq, q.seq,
              aligner_options(index_read_requirement => 2));
\end{lstlisting}
\end{minipage}

MPF is the default active read index. If the table previously selected MPS,
\path{bioseq.set_active_read_index} must select MPF again. This catalog
choice is separate from building the index. Table~\ref{tab:index-read-requirement}
explains the value 2 in the listing.

The code path is concrete: the batch executor prepares a target through
\path{prepare_cpu_persisted_native_target}, which calls
\path{open_exact_minimizer_fragment_image_pg} for grouped MPF.
The resulting reader remains available across query batches for that target.
\texttt{EXPLAIN} can show an executable
\texttt{require\_compatible\_persisted} plan. To establish that a particular
query actually read the index, execution must also succeed and report
persisted targets in \texttt{EXPLAIN ANALYZE}. The custom node's name alone
is insufficient, since transformed-input variants share that name.

Grouped MPS uses its relation-backed streams. The grouped MPF GPU reader
also opens the mapped file, then prepares device data from it. The CPU
worker access explained here is therefore one use of the file.

\subsubsection{What happens when the source changes?}
\label{sec:index-file-consistency}

There is no continuously updated file mirroring a mutable index relation.
For grouped MPF, the relation rows and file are published as one immutable
generation. The following cases explain what that means for SQL writes:
\begin{itemize}
  \item \textbf{Insert a new row with the defaults.} The source row is saved,
    but insertion maintenance is disabled, so no minimizer generation or
    reader file is built for it. A later explicit \texttt{update\_index}
    builds the missing index along with the table's other visible sequences.
    An eligible query requiring persistence fails if it reaches an unindexed
    target. A permissive query can compute its lookup during execution.
  \item \textbf{Enable insertion maintenance.} Ordinary SQL insertion rejects
    grouped minimizer maintenance when an enabled minimizer index has
    \texttt{UPDATE\_ON\_INSERT} policy. It does not update the relation and
    quietly leave the file behind. Section~\ref{sec:index-update-policy}
    explains ordinary maintenance and the separate batched \texttt{bioseq.load}
    path.
  \item \textbf{Update a sequence.} BioseqDB writes a replacement source row.
    Its index must describe that replacement. The old generation cannot serve
    it because readers validate the source identity and visibility before
    opening the file. With insertion maintenance disabled, rebuild after
    committing the replacement.
  \item \textbf{Rebuild the index.} A new generation and file replace the active
    descriptor transactionally. An existing file is not overwritten.
  \item \textbf{Abort the build.} The relation changes roll back. Registered
    abort actions attempt to remove the build's new file after checking its
    identity. A committed file remains available for later queries.
\end{itemize}

\subsubsection{Costs and unfinished work}

A mapping still uses RAM. The operating system loads file pages when they
are touched and can share those pages between read-only mappings. This
avoids retaining a complete private payload copy in every backend. It does
not remove disk reads for a cold file, the temporary buffers used by the
query, or the cost of writing the extra representation.

Closing a reader unmaps its address range and closes its file descriptor.
It does not delete the file. Rebuilding retains retired generations, and
deleting a source row does not remove its reader file. A required read of a missing or
invalid file fails. It does not reconstruct that file during the search.
An explicit rebuild is needed to publish another generation.

These limits are why I treat the path as experimental even though grouped
construction is now enabled by default. Automatic reclamation of retired
files is unfinished. The file is outside PostgreSQL relation WAL, and its
index payload relations are unlogged. File synchronization alone does not
provide crash recovery or a backup protocol that keeps descriptors and
files together.
