\section{A saved index needs a source version}
\label{sec:index-compatibility}

The same table and SQL primary key can survive an update that changes a
sequence. An index must therefore identify more than its owner by name. The
versioned index metadata binds the payload to a source epoch and to the rules
that produced its minimizers. Invalidation changes the old epoch's catalog
state. A replacement source receives a new epoch.

The important checks have simple reasons:
\begin{itemize}
  \item \textbf{Source identity.} The relation, column, source locator,
    epoch, and generation must name the intended source version.
  \item \textbf{Seed meaning.} The alphabet, $k,w$, hash scheme, and scheme
    version must agree with the query. Equal parameter names alone do not
    make different hash schemes compatible.
  \item \textbf{Position meaning.} Width and coordinate encoding must
    represent the target without truncation, including its strand bits.
  \item \textbf{Array meaning.} The reader must recognize the format and
    every addressed range. A device reader also needs a compatible array
    interface.
\end{itemize}

Lengths, offsets, and checksums help detect damaged or misaddressed data.
Checks happen before the reader forms a span or allocates a destination from
an untrusted stored count. A checksum is a corruption check; it does not
replace source-version or algorithm checks. Ordinary serialized minimizer
formats record layout revisions and array sizes, but do not store a source
epoch or hash-scheme identifier. Generation readers also check the stored
source version and minimizer hash scheme.

\subsection{Publish complete generations}
\label{sec:index-generations}
\label{sec:index-physical-persistence}

A small \emph{descriptor} is the record that identifies a generation and its
payload. Building a new generation does not require changing
the old payload in place:
\begin{enumerate}
  \item Allocate a new generation and write its payload.
  \item Check the complete layout and its source and algorithm identities.
  \item Replace the catalog descriptor transactionally, after the payload
    is ready.
\end{enumerate}
The descriptor update uses PostgreSQL's tuple visibility. An older snapshot
can continue to see its older descriptor; a later eligible snapshot can see
the replacement. Failure before publication must not make a partial build
the current index.

A snapshot that sees a parent sequence's deletion must also reject its old
source epoch. These changes belong to the same transaction. Updating a
sequence similarly invalidates the old source for newer snapshots and
appends a replacement. Neither
operation means that every fragment and index byte is immediately erased.
An old reader may still need the former version, and the stored objects need
their own cleanup policy. The current MPS build path does not automatically
delete replaced payloads; reclaiming them requires separate cleanup.

\subsection{From stored index rows to a CPU reader file}
\label{sec:index-mpf5-sidecar}
\label{sec:index-formats}

The optional grouped MPF path keeps two stored copies of its index data.
It first writes index rows in PostgreSQL, then creates a file for CPU reads.
The motivation is repeated searches over a large target. Saving minimizers
avoids computing them again, but a reader may still need to sort positions
and rebuild a lookup structure. Grouped arrays make the saved layout usable
directly. The additional file gives CPU workers stable array ranges without
extracting heap tuples or copying the full payload into each reader.
To understand why, distinguish three objects:
\begin{itemize}
  \item \textbf{The sequence.} The original packed symbols remain in the
    sequence-storage relations from the previous chapter.
  \item \textbf{The index relation.} Separate heap rows hold the computed
    minimizer controls and positions, split into byte chunks, with generation
    metadata. This is already an index, not another copy of the sequence.
  \item \textbf{The reader file.} This file contains the index payload bytes
    in consecutive ranges, their directory and metadata, and an additional
    hash-to-positions section. We call this fixed layout a \emph{reader image}.
    Once published, the image is read-only.
\end{itemize}

The conversion copies the encoded index payload out of the rows. It does
not copy PostgreSQL pages or recompute the minimizers. Heap pages contain
page headers, row headers and other fields around each stored value
\autocite{postgresql17_storage_page_layout}. Mapping the heap file would
still leave those fields between payload chunks. It would not expose one
contiguous index array. The reader image removes that obstacle once during
index construction.

\paragraph{Construction happens once per generation.}
The current relation-backed builder takes these steps:
\begin{enumerate}
  \item \textbf{Build the index rows.} Compute the minimizers and save a new
    generation's payload, directory and metadata in the index relation.
  \item \textbf{Write the reader file.} Reread and check that generation's
    rows in index order. Append their payload bytes to a private construction
    file. Add the directory, metadata and hash-to-positions section, then finish
    and check the file header.
  \item \textbf{Finish the file before publishing the index.} Make the file
    read-only, synchronize it, give it a new final name without replacing an
    existing file, and remove the temporary name. Then update the database
    descriptor and active-generation record in the transaction. Other
    transactions can select the new generation after commit.
\end{enumerate}
The index relation remains after this export. The extra copy costs disk space
and a complete payload reread during construction. The hash-to-positions section
also adds construction work and bytes. In the current writer this section is
always built; the lookup setting chooses how a later query reads the image.
Figure~\ref{fig:index-control-data-plane} shows generation $g$ and its
completed file $F_g$.

\paragraph{Direct lookup uses a hash as a bit address.}
\label{sec:index-direct-lookup}
The extra section combines equal hashes from all fragments of one target
sequence. It has three kinds of data:
\begin{itemize}
  \item \textbf{Membership bits.} Bit $B[h]$ is one when hash $h$ has a
    position list stored in this section. The hash is the bit's address, so it need not
    be stored again as a key beside that list.
  \item \textbf{List records.} Records follow increasing hash order. The
    number of set bits before $h$, called its \emph{rank}, gives its record
    number. Saved counts at each 256-hash boundary make this calculation
    local: add the saved count to the number of set bits before $h$ in that group.
    A record gives the list's start, total count, and number of strand-zero
    positions. Strand-zero positions precede strand-one positions.
  \item \textbf{Positions.} The list start is an entry number in a shared
    position array, not a file-byte offset. Positions include a strand bit.
    When a list has one 32-bit position, the record stores it directly.
\end{itemize}

In Figure~\ref{fig:index-control-data-plane}, hash 5 has one earlier set
bit. Its rank is therefore 1. Record 1 gives start 2 and count 2, so the
reader uses posting entries $[2,4)$, which contain positions 40 and 230.
This is direct addressing followed by a short bit count, with no hash-table
collision search or reconstruction of a target-wide C++ map.

An unset bit means no list is retained in this extra section. It can mean
either that the hash is absent or that its sequence-wide count exceeds the
saved cap, currently 65,534. The original fragment payload remains stored.
A query can impose a lower positive occurrence limit, but cannot exceed the
saved cap on this direct route. The $k=15$ profile used below has $2^{30}$
possible hash values. Its membership bitmap occupies 128~MiB and its saved counts occupy 16~MiB,
before list records and positions. This fixed space cost favors large
targets. It is a file-size cost, not a requirement to keep every mapped page
in RAM at once.

\paragraph{Queries open the file rather than exporting it again.}
The CPU reader first validates the source and reads the generation descriptor
under the query snapshot. It opens the matching file read-only, checks its
identity and size, and maps it with \texttt{mmap}. Mapping gives the process
an address range through which it can read the file. After header and range
checks, the reader uses views of the mapped index arrays. It still allocates
metadata and query work buffers, but does not copy the complete index
payload into a new array. One prepared reader can serve several query
sequences in a batch. A later prepared reader can reopen the same file.

Algorithm~\ref{alg:index-image-lifecycle} separates the two operations.
Here $s$ is the complete, unchanged stored target sequence, $R_g$ denotes
its index rows for generation $g$, and $\sigma$ is the query snapshot.
The named operations are pseudocode, not an API.
File and database errors stop the operation; registered cleanup releases
partly opened resources. The build runs within the caller's transaction.

\begin{algorithm}[htbp]
\caption{Build an MPF reader image once; open it for later queries.}
\label{alg:index-image-lifecycle}
\small
\begin{algorithmic}[1]
  \Procedure{BuildMappedMPF}{$s$}
    \State $g\gets$ a new generation number
    \State $R_g\gets\Call{BuildAndStoreMPF}{s,g}$
    \State $F\gets\Call{CreatePrivateFile}{}$
    \ForAll{payload chunks $c$ of $R_g$, in stored index order}
      \State \Call{CheckChunk}{$c$}
      \State \Call{AppendPayload}{$F,c$}
    \EndFor
    \State \Call{AddMetadataAndDirectLookup}{$F,R_g$}
    \State $F_g\gets\Call{CheckAndPublishReadOnlyFile}{F,g}$
    \State \Call{UpdateDescriptorAndActiveGeneration}{$s,g,F_g$}
    \State \Return $g$ \Comment{the caller commits the transaction}
  \EndProcedure
  \Statex
  \Procedure{OpenMappedMPF}{$s,\sigma$}
    \State $D\gets\Call{ReadAndCheckVisibleDescriptor}{s,\sigma}$
    \State $F_g\gets\Call{OpenAndCheckFileReadOnly}{D}$ \Comment{check identity and size}
    \State $M\gets\Call{MapFileReadOnly}{F_g}$
    \State \Call{CheckHeaderAndRanges}{$M,D$}
    \State \Return a reader using $M$ while the read session owns the mapping and file
  \EndProcedure
\end{algorithmic}
\end{algorithm}

\paragraph{Which SQL queries use the image?}
The public function \texttt{bioseq.update\_index} builds the file when grouped
MPF construction is enabled. Later SQL can reach the mapped CPU reader
through an eligible \texttt{BioseqBatchJoin}. This custom execution node
handles an ordinary inner join whose \texttt{mmsearch} call compares a
stored target column with a query column. The first argument names the
target; the second supplies the queries. In the mapped MPF case, the executor:
\begin{enumerate}
  \item \textbf{Keeps the query rows.} These can include lazy sequence
    values; retaining a row need not load all its symbols.
  \item \textbf{Takes one target row.} Its stored locator identifies the
    target whose compatible index generation must be opened.
  \item \textbf{Opens the existing image.} The reader validates and maps
    the file built earlier by \texttt{update\_index}. Search does not repeat
    that construction.
  \item \textbf{Searches the retained queries.} Query minimizer hashes
    find target positions in the mapped arrays. Those positions supply
    anchors for chaining and alignment. The same reader serves all query
    groups for this target.
  \item \textbf{Moves to the next target.} The target's reader is released,
    while its file stays available for later SQL searches.
\end{enumerate}
A query input with one row is allowed. Two aliases of the same table can
also supply the two inputs. Thus ``batch'' describes how the executor reuses
target preparation, not a separate SQL interface or a requirement to search
two different tables.

The mapped branch currently requires a complete, unchanged stored target,
a compatible CPU profile and generation, and
\texttt{index\_read\_requirement = 2}: \emph{require a compatible stored index}.
An ordinary single-table search such as
\texttt{WHERE mmsearch(r.seq, 'ACGT...')} does not use this mapped reader.
Requiring an index does not turn that scan into the two-input join; an
unsupported required read fails. Even the \texttt{BioseqBatchJoin} name in
\texttt{EXPLAIN} is insufficient, because a separate variant for transformed
operands has the same name and rejects this requirement. The example below
uses plain columns and returns identifiers, leaving the stored target in
the form needed by the mapped reader.

\paragraph{Both approaches still read the input tables.}
Figure~\ref{fig:index-join-read-paths} compares two ways to prepare the
target lookup inside a CPU batch join. In both, \texttt{queries} supplies
query rows and \texttt{refs} supplies target rows. The difference is the
source of the target's minimizer lookup:
\begin{itemize}
  \item \textbf{Ordinary MPF:} read and decode the stored fragment indexes,
    then assemble a private lookup for this join, containing the hashes needed by the retained
    queries. Reuse that lookup across the target's query groups. A cache of
    stored byte chunks can help the reads, but this join still assembles its
    own lookup.
  \item \textbf{Grouped MPF:} open the saved image and use views of its
    arrays. This avoids assembling the private target lookup above.
\end{itemize}
Both still fetch sequence symbols needed for base alignment from sequence
storage. The mapped image supplies the seed index. If no compatible stored
index is used, a third choice is to compute a transient lookup from the
target sequence during the query.

The figure assumes that the two indexes were built beforehand: ordinary
construction with grouped generation disabled on the left, and grouped
construction enabled on the right. The right-hand query must also select
the supported mapped-reader path. Changing the construction setting alone does
not switch the join's reader.

\paragraph{Construction settings and read settings have different jobs.}
\label{sec:index-example-settings}
A GUC is a PostgreSQL configuration setting changed with \texttt{SET}.
Three settings control the construction choices used here:
\begin{itemize}
  \item \texttt{bioseq.aligner.grouped\_soa\_generation.enabled}\newline
    Default: \texttt{off}. Makes \texttt{update\_index} build a grouped generation.
    For MPF this writes both relation rows and the reader image. For MPS it
    writes the separate relation streams. Turning the setting on does not
    itself build an index, convert an older layout, or select a query reader.
    Turning it off later does not remove a completed generation.
  \item \texttt{bioseq.index.async\_persistence.enabled}\newline
    Default: \texttt{on}. Permits eligible background persistence work. It does not
    make an explicit \texttt{update\_index} call asynchronous.
  \item \texttt{bioseq.index.recompute\_async\_persistence.enabled}\newline
    Default: \texttt{off}. Additionally permits a query that recomputes a lookup to
    request persistence for later queries. It needs the preceding setting
    too. Turning it off does not stop a query from building a transient
    lookup to answer the current search.
\end{itemize}

The current deferred implementation rebuilds eligible ordinary MPS indexes.
It stages source identifiers and parameters, then attempts to submit work
when the transaction commits. Abort discards the request. A background
worker reopens the source and checks its policy before rebuilding it.
Queue availability and these checks can prevent persistence, so enabling
both settings does not promise that every recomputed lookup will be saved.
This mechanism does not build the grouped MPF image. Explicit grouped
construction rejects either asynchronous-persistence setting being on;
both must therefore be off in the example.

Listing~\ref{lst:index-mapped-user-path} shows the public calls. It assumes
committed DNA4 sequences with 32-bit packed units in a new permanent
\texttt{refs(id,seq)} table using the Bioseq table access method, and query
sequences with the same alphabet and packing in \texttt{queries(id,seq)}.
Load \texttt{refs} with
\texttt{bioseq.index.insert\_maintenance.enabled = off}. This setting
disables insertion-time index maintenance, including symbol counts; it
avoids creating an ordinary MPF relation during this load. It does not
remove one that already exists. Grouped construction is not an automatic
conversion of that older layout. Other settings not shown retain their
ordinary defaults.

The remaining settings select compatible algorithms and execution:
\begin{itemize}
  \raggedright
  \item \texttt{bioseq.aligner.minimizer.algorithm = 'two\_stack\_nthash'}
    \newline Selects the SIMD implementation with the minimap2 integer hash
    listed in Table~\ref{tab:current-cpu-minimizers}. Construction and search
    must agree on that implementation.
    The accompanying \texttt{kmer\_size} and \texttt{window\_size} settings
    set the query's $k$ and $w$.
    The current grouped builder uses the fixed $k=15,w=10$ profile, so the
    query must match it.
  \item \texttt{bioseq.aligner.chaining.algorithm = 'simd\_minimap2'}
    \newline Selects CPU chaining. Setting
    \texttt{bioseq.aligner.base\_alignment.algorithm} to
    \texttt{'block\_aligner'} selects base alignment. These choices govern later alignment stages;
    they do not change the stored minimizer arrays.
  \item \texttt{bioseq.aligner.vulkan.enabled = off}\newline
    Marks Vulkan as
    unavailable to the aligner. Together with the CPU algorithms and the other default
    settings, this gives a CPU example. It does not rewrite any GPU
    algorithm choices previously made in the session.
  \item \texttt{max\_parallel\_workers\_per\_gather = 0}\newline
    Prevents PostgreSQL
    parallel query workers \autocite{postgresql17_parallel_resources}.
    The current batch path needs an eligible serial query input. BioSeqDB
    can still use its own CPU workers and SIMD instructions.
  \item \texttt{bioseq.index.sequence\_read.enabled = on}\newline
    Allows stored
    reads for permissive searches. The per-call requirement 2 is stronger:
    it forces stored reading and reports a missing compatible index as an
    error. It is an \texttt{aligner\_options} argument, not a GUC.
  \item \texttt{bioseq.aligner.fragment\_minimizer.lookup\_route}\newline
    Selects
    the grouped MPF lookup method. The default \texttt{control\_block\_scan}
    reads fragment controls. The example selects
    \texttt{direct\_compact\_hash\_lookup}, which uses the bitmap and records
    in Figure~\ref{fig:index-control-data-plane}. Both methods map the same
    image; changing between them does not require rebuilding it.
\end{itemize}

\begin{lstlisting}[style=bioseq-index-sql,
  caption={Explicitly build and use the mapped MPF path.},
  label={lst:index-mapped-user-path}]
BEGIN;
SET max_parallel_workers_per_gather = 0;
SET bioseq.aligner.vulkan.enabled = off;
SET bioseq.aligner.minimizer.algorithm = 'two_stack_nthash';
SET bioseq.aligner.minimizer.kmer_size = 15;
SET bioseq.aligner.minimizer.window_size = 10;
SET bioseq.aligner.chaining.algorithm = 'simd_minimap2';
SET bioseq.aligner.base_alignment.algorithm = 'block_aligner';
SET bioseq.index.async_persistence.enabled = off;
SET bioseq.index.recompute_async_persistence.enabled = off;
SET bioseq.aligner.grouped_soa_generation.enabled = on;

SELECT bioseq.update_index('refs'::regclass,
                          'minimizers_per_fragment');
COMMIT;

SET bioseq.index.sequence_read.enabled = on;
SET bioseq.aligner.fragment_minimizer.lookup_route =
  'direct_compact_hash_lookup';
SELECT bioseq.set_active_read_index('refs'::regclass,
                                   'minimizers_per_fragment');
SELECT r.id, q.id
FROM refs AS r JOIN queries AS q
  ON mmsearch(r.seq, q.seq,
              aligner_options(index_read_requirement => 2));
\end{lstlisting}
\end{minipage}

Plain \texttt{SET} survives a successful \texttt{COMMIT}, so the later query
keeps the chosen algorithms and parameters. \texttt{SET LOCAL}, used in the
MPS example below, instead restores the previous session value when the
transaction ends \autocite{postgresql17_set}. The function
\texttt{set\_active\_read\_index} records which index the column's searches
should use; it is a catalog change, not a GUC or an index build.

Grouped MPS reads its relation-backed streams. The grouped MPF GPU path
reads the complete relation payload into device arrays. Neither uses this
CPU reader file.

The mapped path is implemented and callable through public SQL, but remains
an optional, experimental path: construction is disabled by default,
supported query shapes and profiles are restricted, and automatic removal
of retired images and complete recovery support remain unfinished.

\paragraph{RAM is an alternative, not the opposite of a mapped file.}
An index kept in RAM can be fast while it remains available. BioSeqDB's
ordinary index caches already retain prepared CPU objects. However, a new
backend may have to read and reconstruct its own copy, and an index may be
larger than the memory available for that copy.

A mapped file still uses RAM: the operating system keeps file pages in its
page cache. Read-only mappings in different processes can use the same
cached file pages. Pages can be loaded as needed and reclaimed under memory
pressure without making each backend retain the whole index in a private
array. This is the performance reason for the extra representation: avoid
repeated tuple extraction and full-payload copies at query preparation.
It is not a guarantee of faster search. A cold query can wait for page reads,
and a broad lookup can touch much of the file. Building the image also costs
an extra write, checks and synchronization. A warm in-memory index remains
a useful comparison.

\paragraph{Releasing a reader and deleting its file are different steps.}
The file has the following lifecycle:
\begin{itemize}
  \item \textbf{During construction:} a private temporary name identifies
    the unfinished file. Publication installs a distinct final name.
  \item \textbf{On transaction abort:} registered file actions attempt to remove the
    transaction's unfinished or newly published files after checking their
    identity. On commit, the completed file is kept.
  \item \textbf{When a reader finishes:} its PostgreSQL resource owner
    unmaps the address range and closes the file descriptor. The file remains
    available for another reader. Error cleanup releases these resources too.
  \item \textbf{After replacement or source deletion:} visibility and source
    checks decide whether a reader may use the old generation. The current
    query and rebuild paths do not automatically reclaim its retired image.
\end{itemize}

A missing or damaged image causes the required mapped read to fail. The
query does not recreate it from the relation. An explicit rebuild produces a
new generation and image. The file is derived data outside ordinary relation
WAL. Synchronizing it does not establish a recovery protocol or ensure that
a backup contains a matching file and database descriptor.
Its relation-backed generation also uses unlogged payload
relations. Crash recovery, backup and removal of orphaned files therefore
need explicit support rather than an assumption that PostgreSQL manages the
image like a heap relation.
