\section{Selective reads}
\label{sec:index-cold-loading}
\label{sec:index-mps-selective-reads}

Main benefit of MPS is that each group can be a single row within Postgres
(if $n$, $m$ are not causing the array to spill over multiple chunks~\ref{fig:index-storage-layouts}).
This means that minimap2 has to read and check every entry in index, while BioseqDB can only read entiore directory row 
and using $min(hash)$ and $max(hash)$ values to decide if we should read certain groups of minimizers.

The similar logic applies to grouped MPF index as well, but in case of grouped MPF we can also check count array and if the count is very high, then 
we can abandon readind reparate position array at all (the most frequent minimizers should be filtered out as they are not good candiates for anchors). 

The hash-major MPS reader performs the following steps:
\begin{enumerate}
  \item Read and check the complete directory, then find hash ranges that intersect with query hashes.
  \item Read the selected controls to find each key's exact global occurrence count
  \item Apply the occurence count threshold: if the count is high, we don't process this hash
  \item Read the chunks selected by this filtering and read positions form them
\end{enumerate}

\subsection{The reader also determines query execution}
\label{sec:index-reader-execution}

The current CPU MPS builder uses the hash-major format for supported DNA4
profiles. Other alphabets retain the grouped-SoA format. Its older reader
reads and authenticates the complete stored payload, while retaining only the
query's matching positions. The selective-read steps above therefore do not
describe every MPS route.
The native batch path can materialize a shared target for MPF and hash-major
MPS, then run independent queries in parallel. Grouped MPS instead uses the
PostgreSQL scanner path, whose query loop is serial. This follows the worker
boundary in Section~\ref{sec:arch-process-boundary}: workers cannot fetch
PostgreSQL tuples themselves. The choice therefore affects later sequence
access and alignment, as well as index loading.

\subsection{Repeated control scans in MPF}
\label{sec:index-control-scan-waves}

The mapped MPF reader has two lookup routes. Hashes in its supported compact
domain can use direct lookup, described in Section~\ref{sec:index-direct-lookup}.
Wider hashes use the stored control arrays instead. This route counts matching
occurrences, prepares anchor ranges, and then emits anchors through separate
passes over the controls. The current scheduler groups these scans into query
waves limited by worker concurrency, so the controls are visited again for
each wave. The direct route instead attempts to prepare the whole batch at
once, reducing its wave size if memory admission fails
(Section~\ref{sec:arch-admission}). Keeping the file mapped avoids rebuilding
the index, but does not remove repeated traversal or guarantee that its pages
remain in physical memory (Section~\ref{sec:index-residency}).
