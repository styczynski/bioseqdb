  \item As fragment is separate abstraction layer than columnar storage, I also store versions of rows in locators, so deletion just needs to invalidate that version (epoch)

\subsection{Locks protect different parts of the operation}

PostgreSQL distinguishes relation locks, advisory locks, and short locks
inside its buffer manager~\autocite{postgresql17_explicit_locking}. BioSeqDB
uses them for different purposes:

\begin{itemize}
  \item \textbf{Relation locks keep storage available.} Ordinary readers
    and deferred source readers use \texttt{ACCESS SHARE}. It conflicts
    with operations that require \texttt{ACCESS EXCLUSIVE}, such as
    dropping the relation. It permits ordinary concurrent updates and
    deletes.
  \item \textbf{Writer locks coordinate mutations.} Parent update and
    delete operations take a transaction advisory lock for the parent table's
    storage identity. Fragment allocation and writing use their own
    advisory-lock keys.
  \item \textbf{Buffer locks protect a page copy or change.} These short
    locks are released after the page operation. They are not held for
    the duration of an alignment.
\end{itemize}

The combination supports stable snapshot reads without locking every row
returned by a search. It is a description of the implemented read and write
paths, not a claim that every PostgreSQL row-locking feature has identical
behavior in the custom table access method.

\subsection{Removing bytes is a separate maintenance operation}

Deleting one parent row does not immediately erase its fragment rows or its
persistent index payload. This preserves old readers, but also means that
logical deletion alone does not reclaim all occupied space. A reader using
a newer snapshot must reject a source epoch invalidated in that snapshot,
even while its bytes remain present.

Registered fragment relations reject direct update, delete, and truncate
operations. Ordinary vacuum does not compact their live rows into new
positions, because a locator depends on consecutive internal row numbers.
An unused physical tail can be truncated when the required lock is available.

Parent-table maintenance owns the larger cleanup boundary. Dropping or
truncating the parent removes its registered fragment relations.
A full table rewrite reconstructs visible sequence
values in a new storage family and then removes the old family. The current
full-rewrite path can assemble a complete sequence while copying it, so the
bounded fragment-read guarantee must not be extended to that maintenance
operation.

Cleanup can also find orphaned fragment relations or stale registry rows.
This is relation-level cleanup, not a background collector that packs
individual deleted sequences together. Derived index generations have
separate validity and cleanup rules, discussed in the next chapter.
