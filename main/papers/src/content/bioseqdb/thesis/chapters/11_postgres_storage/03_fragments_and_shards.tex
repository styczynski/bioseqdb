\section{Locator implementation}
\label{sec:pg-storage-sequence-indirection}

Sequence locator are implemented as 40-byte struct in C++. The struct must also include the Postgres header so it's effectively 56 bytes in total.
The Postgres header stores alphabet code and base storage unit as \texttt{TYPMOD} field (custom field for storing type modifier).
I don't provide small-sequence optimisation in BioseqDB, because that would complicate the implementation (instead of storing locator for small sequences we can potentially 
store sequence directly in the user table. This would require storing it's padding so potential maximum sequence length that could be stored inline would be $(40B - 1B)*8/2 = 156$ symbols for DNA4).

\begin{minipage}{\linewidth}
\begin{lstlisting}[style=bioseq-cpp26,numbers=none,
  basicstyle=\footnotesize\ttfamily,
  caption={The 40-byte locator stored after the 16-byte sequence header.},
  label={lst:storage-sequence-locator}]
struct sequence_locator {
  std::uint8_t  payload_version;   // format version used by me to change the locator format (currently it's just set to 3)
  std::uint8_t  bucket_index;      // length bucket 0..34
  std::uint16_t reserved_16;       // pad so shard_index is 4-byte aligned, must be 0
  std::uint32_t shard_index;       // fragment relation inside the bucket
  std::uint32_t fragment_count;    // consecutive fragment rows
  std::uint32_t reserved_32;       // pad so logical_length is 8-byte aligned, must be 0
  std::uint64_t logical_length;    // sequence length in symbols
  std::uint64_t first_fragment_row;// row of fragment 0
  std::uint64_t source_epoch;      // immutable source version, must be > 0
};
\end{lstlisting}
\end{minipage}

\begin{itemize}
  \item the internal tables are divided into groups by sequence length and these groups are divided into shards (so I record both of these value to identify sequence)
  \item the number of row for sequence first fragment and number of fragments (i.e number of rows occupied by sequence)
  \item sequence length in symbols (logical length)
  \item version of the sequence in case it's changed (source epoch)
  \item version of locator format (not relevant for users)
\end{itemize}

\info{Locator format optimisation}{
  Currently locators size could be reduces as I don't need to store version (it was used for developent) and I waste too much space for padding. It's potential oppornunity to optimsie in the future (it wasn't a priority as locators occupy overall small space in comparison to sequences themselves).
}

Each sequence as mentioned in section desribing sequence interfaces~\ref{sec:compact-sequence-range} has it's alphabet type and base storage unit.
Base store unit is configurable from SQL. User can declare any power of 2 that is width of supported machine integer:

\begin{minipage}{\linewidth}
\begin{lstlisting}[style=bioseq-search-sql,caption={Examples of different base storage units},label={lst:sql-storage-widths}]
SELECT 'ACTGTGCAACCCCTG'::bioseq.seq('dna4', 64);
SELECT 'ACTGTGCAACCCCTG'::bioseq.seq('dna4', 32);
SELECT 'ACTGTGCAACCCCTG'::bioseq.seq('dna4', 16);
SELECT 'ACTGTGCAACCCCTG'::bioseq.seq('dna4', 8);
-- Example for DNA5 (floor(64/3) = 21 symbols per unit)
SELECT 'ACTGTGCAACCCCTG'::bioseq.seq('dna5', 64);
-- This is illegal as there's no uint128_t. 128-bit unit is just equivalent to two 64-bit units.
SELECT 'ACTGTGCAACCCCTG'::bioseq.seq('dna4', 128);
\end{lstlisting}
\end{minipage}

\info{Sequence fragments}{
\label{info:sequence-fragments}
Sequences are divided into fragments to enable lazy loading.
A fragment is $1024$ packed storage units, so actual bytes occupied depend by the width of storage supplied by the user.
The maximum possible fragment size is for 64-bit storage unit and it's $1024*8B = 8192B$ (note that this goes beyond default postgres page size of $8192B$, because page needs to include the page header as well)
}

Fragment abstraction is a separate layer above columnar storage.
Shards for fragments are internally held as \texttt{CREATE TABLE ... (seq bioseq.seq(...)) USING bioseq}, so each fragment is one TAM row in that single sequence column.

\warn{Storage considerations}{
  \label{warn:storage-considerations}
  Fragments always storing 1024 storage units which works well for long sequences, however if the sequence is short then only small number of storage units will be occupied, while the rest is filled with zeros.
  Compression (default is pglz, but zstd is avialable as well and others for manual building) will take care of this problem and shrink the fragment.
  However it still has measureable effects on processing in the pipeline as BioseqDB will waste space in memory for very short sequences.
  This along with locator format optimisation is a task for future work.
  If we assume occupancy rate of 50\% then minimal sequence size for 32-bit storageshould be $1024 * \frac{32}{2} * 0.5 = 8192$ symbols and for smallest possible storage: $1024 * \frac{8}{2} * 0.5 = 2048$ symbols.
}

\subsection{Two levels of sharding}

Postgres tables have limits on the number of stored rows, so in the most
extreme cases the amount of sequence data can be more than one table can hold,
especially if we store many full human genomes.
A (single copy i.e haploid) human genome is about $3.1$ to $3.2$ billion bases ($3.2\times 10^{9}$ symbols and the $32$-bit DNA4 unit from the figure above).
PostgreSQL documents a maximum table size of $32$ TB at $8192B$ default page size~\autocite{postgresql17_limits}. That
bound is a result of internal Postgres $32$-bit page index.

\begin{equation}
\begin{aligned}
  F &= 1024 \times \frac{32}{2} = 16\,384
    && \text{symbols per fragment}\\
  n_{\mathrm{frag}} &= \Bigl\lceil \frac{3.2\times 10^{9}}{F} \Bigr\rceil = 195\,313
    && \text{fragment rows per genome}\\
  B &= 16 + 1024 \times 4 = 4\,112
    && \text{bytes per fragment row}\\
  P &= 8192 - 24 = 8\,168
    && \text{usable bytes per page}\\
  n_{\mathrm{page}} &= \Bigl\lceil \frac{n_{\mathrm{frag}} B}{P} \Bigr\rceil = 98\,327
    && \text{pages per genome}\\
  n_{\mathrm{seq}} &= \Bigl\lfloor \frac{4\,294{,}967{,}294}{n_{\mathrm{page}}} \Bigr\rfloor = 43\,680
    && \text{genomes in one table}
\end{aligned}
\label{eq:storage-human-genome-table-cap}
\end{equation}

Without compression, one fragment table can therefore hold about $43{,}680$
human-genome sequences before it runs out of pages. Practically compression rates for human genomes were already measured~\cite{kryukov_comparison_of_fasta_hg_compression}
and zstd is capable of compressing a human genome to effectively $790$ MB ($7.9\times 10^{8}$ bytes).
With that size, each genome occupies $96{,}719$ pages, so the same limit allows $44{,}406$ genomes in one table.

\info{Table limits}{
  I present this calculation to present that hitting the table limit isn't very improbable. There exist datasets bigger than this limit.
  To prvent users from hitting limit and requiring them to manually spli tables, I decided to provide internal sharding.
}

The internal sharding allows fragments to spill over into multiple tables. If the underlying table achieves $1TB$ limit (which is lower than theoretical $32$ Postgres limit), fragements are stored in newly created columnar relations.
The sharding is two-level:
\begin{itemize}
  \item length bucket: groups sequences by their logical number of symbols - precisely $max(0, min(\left\lfloor log_2(|s|)\right\rfloor - 8, 34))$ is the bucket index.
  \item shard: inside one length bucket BioseqDB can create multiple tables when existing tables reach $1TB$ limit (potentially to store extremally large datasets)
\end{itemize}

The current layout has 35 buckets. The first covers lengths $[0, 2^8)$ and each next bucket covers $[2^i, 2^{i+1})$ for $i=8..40$.
The largest bucket is designated to store sequences longer than $2^{41}$ symbols.

\warn{Sharding limitations}{
  It's very important to note that current during stream access policy~\ref{fig:sequence-scan-lifecycle} the sequence size is not known until its end is reached, thus my
  code in BioseqDB decides to store the sequence in the largest bucket (34) even when the sequence is short.
  This code path is utilised by IO submodule that loads sequences from FASTA file.
  This means that each sequence loaded from FASTA currently will be stored in the largest bucket.
  I plan to resolve this problem in the future - solution could be adding ability to IO submodule to search for first sequence end and assume all sequences are similar sizes. Alternatively I could write one sequence and then adjust the bucket after size is known.
  Both of these solutions however add additional overhead and complexity to the FASTA loader module.
  Additionally length-based sharding can allow better utilisation of fragments memory (so fragments are smaller even without compression~\ref{warn:storage-considerations} 
  and they require fewer bytes when allocated in RAM)
}
