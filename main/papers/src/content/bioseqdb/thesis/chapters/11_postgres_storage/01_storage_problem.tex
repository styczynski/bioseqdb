\section{Store sequences together with their metadata}
\label{sec:pg-storage-role}

I already mentioned before for example when discussing sequence abstractions~\ref{sec:sequence-abstractions} that I usually operate on locators, that just point to location where actual sequence is stored.

PostgreSQL already has mechanism for that: it stores large values out of line (outside actual row) through TOAST~\autocite{postgresql17_toast}. 
This mechanism however, has it's limitations - it's storage is limited to 1GB per row, which is an effect of maximum width of integer storing row's OID (object indentifier is internal numbering scheme in Postgres).
If we assume that DNA4 sequence is bit-packed and it's entire human genome (lengths of around 3.1 - 3.2 Gbps) this gives us conservatively $3 * 10^{9} * \frac{2}{8}B = 750MB$ of storage per row.
If we want to store both pairs of chromosomes we can pesimisitcally require $1.6GB$ of storage per row. 
In most cases researchers split the sequence into smaller chunks, but this is manual process requiring additional tools.

Moreover, most of the workflows are OLAP-type.: user is expected to do bulk inserts, do not perform frequent updates and deletes when running alignment.
Usual TOAST wouldn't take advantage of that specific workflow assumption as we cannot read TOAST in bulk.

That's why I decided to implement custom TOAST-like mechanism in BioseqDB and use columnar storage appropiate for OLAP workflows:
\begin{itemize}
  \item \textbf{User table} holds all the data in columnar format, where the sequence column itself is replaced with small locator object that points to sequence fragment.
  \item \textbf{Sequence fragments} are stored in multiple sharded tables that are normally invisible to the user. All of these tables also use columnar storage, so short sequences are treated the same way as metadata in columnar context - they will be merged into one batch. I call these batches of rows "strips" in the code.
  \item \textbf{Persistent indexes} are separate entities stored as tables that are normally not visible to the user as well. They are responsible for providing pre-computed objects for sequences. There's small abstraction layer in BioseqDB which allows to extend it by adding different types of indexes that provide different information.
\label{lst:types-of-storage-entities-in-bioseqdb}
\end{itemize}

\warn{Adapted from Citus and Hydra Columnar}{
BioSeqDB's columnar layer adapts code from both Citus Columnar and Hydra
Columnar~\autocite{citus_columnar_storage,hydra_columnar_source}.
Hydra extended the Citus code with features including very primitive vectorized SQL
execution and a cache of stripes. In BioSeqDB I modernized the adapted C code by rewriting it completely into C++26 modules with automatic code generation and added support for newer PostgreSQL 19.0 (which in case of Hydra original codebase was not supported).
Only small of the original code was left untouched. This code was used as a low-level storagebase, where concepts like sequence locators, fragment readers, and sequence indexes are purely my innovations.
}

The linked Hydra columnar documentation was unavailable as the theam building it moved to create a different database system. 
Although I was basing my implementation in the Hydra codebase, understanding the chunk operations required multiple manual investigations to understand it completely~\autocite{hydra_columnar_source}.
Current BioseqDB storage design is an effect of this process.

It's worth noting that I mention both Citus~\autocite{citus_distributed_2021} and Hydra sources here as Hydra was fork of Citus that diverged at some point to later be abandoned. Citus columnar is still actively maintained but it lacks features like row deletion, vectorization and it's very simple columnar interface.
Meanwhile Hydra offered these features, but due to being abandoned didn't correctly build for newer Postgres version and lacked bugfixes done by Citus team since the forking moment.
Modernizing the Hydra codebase thus involved not only manually inspecting the code, but also tracking commits between Hydra and Citus. This work thus was complicated and very time-consuming involving also detection of new bugs in Hydra code that were undected after retirement of the project.
