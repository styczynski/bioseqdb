\section{Alignment as a PostgreSQL execution primitive}
\label{sec:postgres-custom-scan-scope}

The alignment pipeline described in the preceding chapters is not naturally a
scalar SQL function.  Its useful unit of work is a batch of sequence pairs,
its result for one pair is a set of matches, and its implementation may need
to retain an index, submit work to a scheduler, or materialize a query
collection before it emits the first row.  PostgreSQL, in contrast, initially
sees an SQL predicate as an expression that is evaluated once for each input
tuple and returns one value.  The main purpose of the BioSeqDB PostgreSQL API
is to reconcile these two execution models.

The public expression is deliberately ordinary:

\begin{lstlisting}[language=SQL]
SELECT t.pk,
       bioseq.score(t.pk),
       bioseq.target_start(t.pk),
       bioseq.target_end(t.pk),
       bioseq.cigar(t.pk)
FROM target_sequences AS t
WHERE mmsearch(
        t.sequence,
        'ACGTACGT...'::bioseq.seq('dna4', 32));
\end{lstlisting}

Here CIGAR denotes the Concise Idiosyncratic Gapped Alignment Report that
encodes the alignment edit path.

The parser can resolve the types of this statement without learning a new SQL
grammar.  It produces a normal \texttt{FuncExpr} for \texttt{mmsearch} and
normal function expressions for the projected match fields.  Nevertheless,
the executor must not call those expressions in the ordinary way.
\texttt{mmsearch} is a \emph{rendezvous expression}: it marks the semantic
location of sequence search so that a custom execution node can claim it.
The projected helpers name fields of the match currently being emitted by
that owner.  They do not each run another alignment.

This distinction is visible in cardinality.  Let input row \(i\) produce
\(m_i\) accepted alignments.  The custom scan emits

\[
    N_{\mathrm{out}} = \sum_{i=1}^{N_{\mathrm{in}}} m_i ,
    \qquad m_i \in \{0,1,2,\ldots\}.
\]

Thus a source row with no match vanishes, one with one match behaves like an
ordinary filter result, and one with several matches is repeated with
different match-field values.  A Boolean function can say whether
\(m_i>0\), but it cannot supply the \(m_i\) rows or ensure that score,
coordinates, CIGAR, strand, and mapping quality all refer to the same member
of that set.

semantic requirement rather than only a batching optimization.

The final design therefore treats SQL syntax, planner ownership, and executor
cardinality as one contract.  A supported \texttt{mmsearch} must be consumed
by exactly one BioSeqDB node.  A query shape that cannot satisfy this contract
fails closed.  It is not permitted to fall through to a permissive Boolean
implementation, because doing so would turn an unsupported alignment query
into a query that silently accepts every row.

\section{The SQL surface is a rendezvous, not a hidden mode switch}
\label{sec:mmsearch-sql-rendezvous}

\subsection{Two typed entry points}

The current extension exposes a two-argument search with session defaults and
a three-argument form with a typed options value.  In schematic form their
signatures are

\[
\begin{aligned}
  \operatorname{mmsearch} &: (\texttt{bioseq.seq},
      \texttt{bioseq.seq}) \rightarrow \texttt{boolean},\\
  \operatorname{mmsearch} &: (\texttt{bioseq.seq},
      \texttt{bioseq.seq},
      \texttt{bioseq\_aligner\_options}) \rightarrow
      \texttt{boolean}.
\end{aligned}
\]

The SQL declarations expose the two signatures together with volatility and
parallel-safety metadata.  Both name \texttt{mmsearch\_support} as their
PostgreSQL support function.  The signatures let the parser resolve argument
and result types.  The support function participates in planner costing
through PostgreSQL's documented interface~\cite{postgresql17_support_functions}.
None of this means that the scalar C++ body performs alignment.  The body raises
\texttt{ERRCODE\_FEATURE\_NOT\_SUPPORTED} with the message
\emph{``mmsearch qualifier has no Bioseq executor owner''}.  The three-argument
entry point preserves SQL null behavior for null operands before reaching that
error boundary.

This fail-closed body is important for two reasons.  First, PostgreSQL can
copy or move expression trees during planning.  If an unexpected copy
survives as a filter, it produces a visible error rather than false-positive
biological results.  Second, behavior does not depend on a thread-local flag
set by the scan.  A hidden flag would make an immutable function return
different values for the same arguments, would interact badly with constant
folding, and could remain stale after PostgreSQL's non-local error unwinding.
The owner is instead represented explicitly in the plan tree.

\subsection{Match projections}

The same SQL module defines the typed projection families summarized in
Table~\ref{tab:match-placeholder-types}.  A query can request only the fields
needed by its result:

\begin{lstlisting}[language=SQL]
SELECT t.pk,
       bioseq.mapq(t.pk),
       bioseq.is_reverse(t.pk),
       bioseq.edit(t.pk)
FROM targets AS t
WHERE mmsearch(t.seq, $1::bioseq.seq('dna5', 64))
  AND bioseq.edit(t.pk) < 20;
\end{lstlisting}

The apparent argument \texttt{t.pk} is an ownership anchor.  It lets the
planner and custom scan associate the helper with the row and target lineage
that produced the match.  It is not the storage location of the score.  The
executor later replaces an attributable helper expression with a typed
placeholder node.  A helper that refers to the wrong target recipe is not
silently populated from whichever alignment happened to run.

The design also avoids optional work.  During \texttt{BeginCustomScan}, the
owner derives a requested-field mask from the expressions that survived
planning.  That mask gates traceback construction and secondary metrics.
Per-call options are then overlaid on a snapshot of the session settings.
The dispatcher records the pipeline selected for that scan.  Projection
pruning can therefore reduce work without changing any requested field.

\section{Planner support, costs, and exact ownership}
\label{sec:planner-support-and-ownership}

\subsection{Why the ordinary expression has a high cost}

PostgreSQL calls \texttt{mmsearch\_support} with a
\texttt{SupportRequestCost}.  The function reports startup cost \(100000\)
and per-tuple cost zero for the ordinary scalar expression.  This value
discourages PostgreSQL from treating an unowned call as a cheap Boolean
predicate.  It does not locate \texttt{mmsearch}, validate its shape, or
establish executor ownership.  Those tasks belong to the relation and join
path hooks, which inspect expression identity, arity, provenance, and the
containing \texttt{RestrictInfo}.

The first proof of concept paired the large scalar cost with a custom-path
cost near \(-100000\).  This made the desired path win an artificial cost
race.  It demonstrated custom-scan selection, but it did not establish that
every retained alternative had valid semantics.\footnote{DOC0052,
archived, records the true-returning stub, mutable score constant, and
negative custom-path cost.}  The current implementation uses no negative
sentinel.  The \(100000\) startup cost belongs only to the unowned scalar
alternative and is excluded from an owner's cost tree.

For an owning base scan, the conceptual cost is

\[
\begin{split}
 C_{\mathrm{owner}} ={}&
 C_{\mathrm{storage}} +
 C_{\mathrm{operands}} +
 C_{\mathrm{alignment}}(L_t,L_q,B,I)\\
 &+ C_{\mathrm{residual\ quals}} +
 C_{\mathrm{projection}} ,
\end{split}
\]

where \(L_t\) and \(L_q\) are estimated target and query symbols, \(B\) is
the dispatch capacity, and \(I\) records whether the planned index contract
permits an attempt to read a stored index.  It does not assert that a
compatible generation exists.  Presence and compatibility remain runtime
checks.  Join ownership additionally accounts for complete query child
materialization, target-child scanning, residual join expressions, and
estimated result rows.  Every component is clamped to a finite nonnegative
PostgreSQL cost.  An incumbent path's cost may be retained as EXPLAIN
evidence, but it is not used as a magic threshold.

\subsection{A semantic operation cannot be selected by cost alone}

A cost comparison is valid only when both paths implement the same semantics.
An owner and a path that executes the fail-closed rendezvous body are not such
alternatives.  Current planning therefore separates three decisions:

\begin{enumerate}
  \item Structural checks identify one supported \texttt{mmsearch} call and
  its exact \texttt{RestrictInfo}.
  \item A custom path is constructed only after target and query provenance,
  parameterization, and execution capabilities have been validated.
  \item Once ownership exists, alternatives carrying an executable copy of
  that exact restriction are removed.
\end{enumerate}

There is also a broader relation-access policy.  When custom scanning is
enabled for a BioSeqDB columnar relation, the relation hook removes
non-\texttt{IndexPath} alternatives before adding its custom paths.  This
general path pruning is distinct from semantic ownership.  Ownership follows
the exact restriction through base restrictions, parameterized path
information, and join restrictions.  The operation is therefore identified
structurally.  Cost only describes the alternatives that remain meaningful.

from scalar cost metadata.

\subsection{Relation and join hooks}

BioSeqDB registers both a relation-path hook and a join-path hook.  For a
\texttt{USING bioseq} relation, \texttt{BioseqColumnSetRelPathlistHook}
first allows normal PostgreSQL and the columnar table access method to
construct their paths.  \texttt{AddBioseqColumnScanPath} then builds a
\texttt{CustomPath}, copies the relation's \texttt{PathTarget}, gathers the
base and parameterized restrictions available at that path, and searches for
an exactly ownable \texttt{mmsearch}.  The recursive path builder explores a
bounded subset of parameterizations because join clauses may make an outer
relation's value available as a \texttt{PARAM\_EXEC} input.

For an INNER join whose restriction itself contains one semantic
\texttt{mmsearch},
\texttt{BioseqBatchJoinSet}\allowbreak\texttt{JoinPathlistHook} can construct a
join-level owner.  It either retains a proven parameterized base-scan owner or
constructs a \texttt{BioseqBatchJoin} path with target and query children.
Lazy slice or other evaluated operands may require a
\texttt{BioseqSliceProject} provider and a per-row recipe.  These shapes are
discussed in Section~\ref{sec:mmsearch-join-ownership}.

The hooks are deliberately conservative.  A call must have a recognized
function object identifier (OID) and arity, and its options must fold to the
supported form.  Target and query recipes must have attributable lineage and
compatible typmods.  Planner placement must preserve row security, volatility,
and parameterization.  Providers and parallel properties must satisfy the
selected lifecycle.  More than one semantic join-level call is rejected with
guidance to split the predicates into separate query levels.  A failed check
means that the hook does not claim the expression.  It never authorizes scalar
fallback.

\subsection{What crosses the planning boundary}

PostgreSQL's \texttt{CustomPath} and \texttt{CustomScan} offer several lists
for extension data.  BioSeqDB assigns them narrow roles:

\begin{itemize}
  \item \texttt{custom\_restrictinfo} identifies the exact restriction owned
  by the path.  It supports planning proofs.  The expression is not left in an
  executor qualifier.
  \item \texttt{custom\_paths} carries child paths, such as the locator-side
  BioSeqDB scan and the query child of a batch join.
  \item \texttt{custom\_private} stores versioned integer tags, relation and
  attribute identities, typmod/layout data, source recipes, and diagnostic
  costs.  It contains PostgreSQL nodes that can be copied and serialized, not
  live C++ objects.
  \item \texttt{custom\_exprs} stores expressions that must pass through
  PostgreSQL's \emph{setrefs} machinery.  In the base scan, the fourth entry
  carries the owned \texttt{mmsearch} expression as executor-only state.  An
  outer \texttt{Var} can therefore become the correct \texttt{PARAM\_EXEC}
  without making the expression an executable qualification.
\end{itemize}

\texttt{PlanCustomPath} removes the owned expression from
\texttt{scan.plan.qual} and asserts that no \texttt{mmsearch} remains there.
It also prevents the vectorized qualification list and the storage pushdown
list from retaining a copy.  This is more than a cosmetic EXPLAIN cleanup:
each of those lists corresponds to an execution site that otherwise could
call the fail-closed SQL body.

Hidden child outputs are installed in the \texttt{PathTarget} before plan
construction.  This timing matters because PostgreSQL's setrefs pass can only
replace expressions with child-output \texttt{Var} nodes when the child
already promises to publish them.  Adding a target-list expression later in
the executor would be too late for upper joins, results, aggregates, or
\texttt{RETURNING} projections to bind to it reliably.

\subsection{Plain EXPLAIN does not allocate the aligner}

\texttt{CreateCustomScanState} constructs only the executor-state shell.
Pipeline objects, query copies, sequence providers, buffer arenas, and
accelerator resources are initialized in \texttt{BeginCustomScan}.  A plain
\texttt{EXPLAIN} can therefore inspect the plan without opening an alignment
session.  \texttt{EXPLAIN ANALYZE} follows the normal executor lifecycle and
adds observed counters after the node runs.

This separation also keeps plan serialization meaningful.  A prepared
statement may outlive the memory in which it was planned.  A parallel or
cached plan cannot safely contain a pointer to a C++ scheduler object.
Versioned PostgreSQL node metadata survives copying, while the runtime is
rebuilt under the query's memory and resource owners.

\section{Batch execution and zero, one, or many outputs}
\label{sec:customscan-batch-state-machine}

\subsection{The write, process, and read state machine}

The base scan uses a two-phase state machine implemented by
\texttt{Inner\_CustomExecScan} and the dispatch buffer.  ``Two phase'' does
not mean that the entire relation must be retained.  The current buffer has a
capacity of 8192 submissions.  Reaching capacity closes and processes the
current batch, drains its cursors, releases its copied slots, and resumes the
still-live access-method scan.  End of input performs the same transition for
the terminal partial batch.

Algorithm~\ref{alg:customscan-write-read} shows where stable row capture,
alignment dispatch, and match-by-match projection occur.

\begin{algorithm}[htbp]
\caption{Conceptual execution of a scan-owned \texttt{mmsearch}}
\label{alg:customscan-write-read}
\small
\textbf{Initialization.} Initialize an empty dispatch buffer and per-scan
runtime.

\textbf{Loop.} While the source is not exhausted or buffered output remains,
repeat the applicable branch:
\begin{enumerate}
  \item \textbf{Read mode.}
    \begin{enumerate}
      \item Set \(o \gets\) the next match cursor entry.
      \item If \(o\) exists:
        \begin{enumerate}
          \item Populate all requested placeholder constants from \(o.match\).
          \item Temporarily promote lazy sources needed by the projection.
          \item Emit \textsc{Project}(\(o.input\_row\), placeholders).
          \item Restore the stable locator-backed input row.
        \end{enumerate}
      \item Otherwise, if the source is exhausted, return end of scan.
      \item Otherwise, release the completed physical batch and return to
            write mode.
    \end{enumerate}
  \item \textbf{Write mode.}
    \begin{enumerate}
      \item Set \(r \gets\) the next scalar row or the next kept row from a
            vector batch.
      \item If \(r\) does not exist, mark the source exhausted and process the
            terminal batch.
      \item Otherwise:
        \begin{enumerate}
          \item Evaluate residual qualifications and owned operand
                expressions.
          \item If the residual frontier passes and operands are non-null:
            \begin{enumerate}
              \item Copy stable row/source references into the dispatch arena.
              \item If the buffer reaches capacity, process the batch and
                    construct per-input match cursors.
            \end{enumerate}
        \end{enumerate}
    \end{enumerate}
\end{enumerate}
\end{algorithm}

During the write phase PostgreSQL owns the active scan slot and is free to
reuse it on the next access-method call.  The buffer therefore copies the
tuple representation it needs and retains stable sequence-source
descriptors.  During the process phase the selected mapper consumes the
captured target/query inputs and builds an output map.  During the read phase
each cursor entry pairs one copied input row with one
\texttt{MatchResult}.  The scan installs that input as
\texttt{ecxt\_scantuple}, updates the placeholders, calls
\texttt{ExecProject}, and returns one virtual tuple to its parent.

An input with zero matches has no cursor and produces no row.  An input with
three matches is visited three times by the read phase, with the same stable
input attributes and three different sets of placeholder values.  This
provides set-valued behavior through PostgreSQL's pull executor without
exposing a set-returning function in the SQL surface.

\subsection{Scalar and vectorized access converge before alignment}

The table access method can yield a scalar slot or a vector slot.  In the
vectorized path, pushable ordinary qualifications produce a keep mask, after
which the scan extracts each retained row into its scalar slot.  Both paths
then reset the per-tuple expression context, establish
\texttt{ecxt\_scantuple}, evaluate the residual frontier and any authoritative
target/query \texttt{ExprState}, and call the same submission interface.
Alignment itself is therefore not skipped merely because table filtering was
vectorized.

An early vectorized path advanced through input without invoking the submission
callback.  The archived DOC0058 fixture later produced identical rows with
vectorization enabled and disabled.  Current named regression fixtures in
\texttt{main/bioseq/integration\_tests/test\_mmsearch.cpp} exercise the same
parity requirement for covered base-scan and join shapes.  These tests
demonstrate the invariant for those fixtures.  They do not prove parity for
every possible SQL expression tree.

\subsection{Lazy sequence sources and tuple lifetimes}

Chapter~9 showed that a sequence value may be a compact inline value, a
fragment locator, or a lazy recipe.  The custom scan is the point at which
PostgreSQL tuple lifetime and sequence-source lifetime meet.  A deferred
table scan can leave a stable locator in the buffered row instead of eagerly
assembling every sequence.  The alignment provider bulk-acquires the
fragments required for the current dispatch.  Output-only sequence
expressions are promoted just before projection and then restored to the
locator form.

The restoration step is necessary when one row has several matches.
PostgreSQL resets the per-tuple memory context between returned rows.  If the
buffered slot were overwritten with a detoasted or assembled pointer owned by
that context, the second match would dereference released memory.  Current
code captures the source cells before promotion and restores them on normal
return, C++ exception, and PostgreSQL \texttt{longjmp}.  Match objects and
copied minimal tuples live in the batch arena.  Ephemeral expanded objects
remain confined to the current projection.

\subsection{A lower-bound prefilter does not become the SQL predicate}

When a prefilter such as SneakySnake is enabled, it is permitted to reject a
candidate only according to its proven lower-bound contract.  Every survivor
still reaches exact alignment.  If SQL additionally requests a strict
edit-distance condition, the read phase evaluates that exact boundary against
the resulting \texttt{MatchResult}.  This ordering prevents an accelerator
gate from becoming an approximate implementation of the user's SQL
predicate.

\section{Injecting match fields into planned expressions}
\label{sec:match-placeholder-injection}

\subsection{Mutable typed Const nodes}

PostgreSQL evaluates a projection from an expression tree.  Rebuilding that
tree for every match would be expensive, while calling each SQL helper would
have no access to the scan's current match.  BioSeqDB instead rewrites each
owned helper to a typed \texttt{Const}.  The node address remains stable for
the executor lifetime and only its \texttt{constvalue} and
\texttt{constisnull} fields change.

On the first call to \texttt{CustomExecScan}, the scan allocates the
placeholder family and runs \texttt{var\_injector\_mutator} over the finalized
target list.  The mutator recognizes function OIDs, verifies that the helper
belongs to this match-owner recipe, and substitutes the corresponding
\texttt{Const}.  Unrelated functions are traversed normally.  A projected
\texttt{bioseq.edit} whose target argument does not match the
\texttt{mmsearch} target raises a diagnostic instead of receiving fields from
the wrong sequence.

Before each \texttt{ExecProject},
\texttt{populate\_placeholder\_consts} copies one
\texttt{MatchResult} into the requested nodes.  Coordinates and lengths use
PostgreSQL \texttt{BIGINT}, because the C++ source values are unsigned
64-bit sequence sizes.  Edit distance also uses a \texttt{BIGINT}
placeholder.  Scores, map quality, and seed counters remain \texttt{INT4}
because their source fields are 32-bit.  Strand and status use
\texttt{BOOLEAN}, divergence uses a floating type, and CIGAR is formatted as
PostgreSQL text only when a CIGAR placeholder exists.

the semantic sense.  It is installed only after planning and setrefs have
finished.  PostgreSQL never has an opportunity to fold its changing value
during planning.  The target list is compiled against the stable node, and
the scan mutates it immediately before projection.

\subsection{Why joins need PlaceHolderVar}

A bare helper such as \texttt{bioseq.cigar(t.pk)} can be copied or pushed into
a join child's target list.  In an outer join, the result also carries
null-extension semantics: the helper must become null when the originating
side is null-extended.  Replacing every visible copy with an unqualified
\texttt{Const} would lose that placement and nulling information.

The support function \texttt{bioseq\_placeholder\_support} handles
\texttt{SupportRequestSimplify}.  When the query contains joins or
aggregates, it finds the originating \texttt{Var}, copies the helper, and
wraps it with PostgreSQL's \texttt{PlaceHolderVar}.  The wrapper preserves
\texttt{phlevelsup}, \texttt{phrels}, and \texttt{phnullingrels}.  PostgreSQL
can then carry the value upward from the correct evaluation level without
re-evaluating the helper in a sibling scan.  At executor rewrite time, the
wrapper remains intact while its contained owned function is replaced.  The
placement and nulling fields follow PostgreSQL's primary node
definition~\cite{postgresql17_placeholdervar}.

This mechanism was introduced after a LEFT JOIN plus CIGAR projection exposed
a crash: the planner had pushed a helper into a child that had no current
\texttt{MatchResult}.  It also solves aggregate placement, where a projected
match field must be computed below the aggregate rather than invoked after
the alignment owner has been drained.  The current helper support is
deliberately a placement mechanism.  Exact ownership is still checked by the
custom scan.

\subsection{Stable identity is more precise than function OID}

Function OID alone is insufficient when a query contains multiple sequence
relations, aliases, slices, or nested owners.  Two
\texttt{bioseq.target\_start(...)} calls have the same OID but may refer to
different alignments.  Current owner descriptors therefore carry the target
recipe, base lineage, relation/attribute identities, placeholder identity or
\texttt{phid}, and stable match-site information.  A descendant owner may
publish an already-computed helper to an upper result.  The upper owner must
pass it through rather than relabeling it as its own.

This is the database analogue of keeping fields from one mapper record
together.  The stable identity guarantees that coordinates, CIGAR, and score
are not assembled from different match rows merely because their function
names coincide.

\subsection{Raw BioseqBatchJoin}

For the raw two-child case, the query child is fully materialized before the
first output.  The target child is a BioSeqDB locator scan and is read once.
The batch join can then combine target rows with retained query references,
dispatch the alignment work, and publish each match together with the
corresponding child columns.  Its startup cost includes the entire query
child and materialization work.  Its total cost adds the complete target scan,
operand evaluation, alignment, residual qualifiers, and output rows.

This plan is not equivalent to merely placing a custom node above an existing
NestLoop, HashJoin, or MergeJoin.  The child join path may already contain the
\texttt{mmsearch} as a join filter.  BioSeqDB reconstructs a private child
path with the exact \texttt{RestrictInfo} removed, or declines the
transformation.  It never wraps a descendant that would still call the SQL
rendezvous function.

\subsection{Parameterized scans and rescans}

When PostgreSQL chooses a nested parameterized plan, the query operand may be
a \texttt{PARAM\_EXEC} supplied by the outer row.  \texttt{BeginCustomScan}
records the exact post-setrefs argument cell and initializes
\texttt{MmsearchParamRebind}.  On \texttt{ReScanCustomScan}, the scan clears
match cursors, retained slots, provider state, and source exhaustion, then
re-evaluates the parameter from the owned expression before rescanning the
table access method.

This explicit rebind replaced an early approach that inspected only constants
at initialization.  Without it, the first outer query could be reused for
later outer rows, producing plausible but wrong join results.  ReScan is
therefore not only a performance callback.  It is part of the SQL correlation
semantics.

\subsection{Removing every executable copy}

PostgreSQL may represent the same semantic restriction in several
planner/executor locations.  The current EXPLAIN audit names five classes:

\begin{enumerate}
  \item Owned \texttt{RestrictInfo} path copies.
  \item Executable \texttt{mmsearch} qualification copies.
  \item Vector-qualification copies.
  \item Storage-pushdown copies.
  \item Descendant owner copies.
\end{enumerate}

For each audited join fixture, these counters must be zero below the
authoritative node and \texttt{Bioseq Residual Mmsearch Qual} must be
\texttt{absent}.  The regression helper also checks the enumerated textual
plan sites for an \texttt{mmsearch} expression.  Together, these checks
demonstrate that the tested call did not survive at the audited execution
sites.  They are stronger than checking only for the presence of
\texttt{BioseqBatchJoin}, but they are not a proof over every PostgreSQL
transformation or arbitrary query shape.

\subsection{Security and evaluation order}

Expression-tree surgery must respect PostgreSQL security and volatility
rules.  The first join-level implementation declines row-security shapes,
pseudoconstant or non-promotable restrictions, and volatile sibling
qualifiers whose relative evaluation order it cannot preserve.  The optional
third argument must fold to the expected typed constant form before the hook
claims it.  Parallel child plans are rejected where the provider lifecycle
cannot be transferred safely.

These checks intentionally sacrifice some plan shapes.  A database extension
cannot justify moving a volatile expression, bypassing a security barrier, or
reusing a value across rows.  Producing a larger alignment batch does not
change that constraint.  Unsupported shapes remain visible through the
fail-closed SQL boundary.

\section{What BioSeqDB borrowed from ParadeDB}
\label{sec:paradedb-customscan-comparison}

The vendored \texttt{paradedb-experiments} repository provided a concrete
PostgreSQL extension example in which planned projection helpers are
substituted by executor-owned values~\cite{paradedb_pg_search_customscan}.
Its PDB scan recognizes score and snippet projections, injects typed
placeholder constants, and updates \texttt{const\_score\_node} with the score
of the current search hit.  Its \texttt{placeholder\_support} also wraps
projection expressions in \texttt{PlaceHolderVar} for joins and aggregates,
preserving \texttt{phlevelsup} and \texttt{phnullingrels}.

These mechanisms answered an important feasibility question: an extension
does not need custom SQL syntax for every result field.  It can allow
PostgreSQL to parse an ordinary function call, preserve the expression's
placement through planning, and replace the call with an executor-local
value at the custom scan boundary.  The early BioSeqDB proof of concept
adapted this pattern for one synthetic score.

The complete BioSeqDB problem is nevertheless different.  Text search
commonly associates one score with one hit already enumerated by the search
node.  Sequence search must itself create a variable number of match rows
after batch processing.  Its target value may be a large lazy sequence
locator rather than a value that can be held in a conventional tuple datum,
and each match has a coordinated record of scores, coordinates, strand,
traceback, and mapping-quality fields.

\subsection{Why the true-returning stub was especially dangerous}

Returning true looked convenient during the first experiment because it kept
the predicate in the planned tree while the custom scan supplied synthetic
scores.  It also meant that any planner path which did not perform the custom
rewrite returned every row.  A cost estimate then became a correctness
mechanism: if the custom path ever lost, SQL results changed.  The final
erroring body reverses this default.  A new PostgreSQL transformation, a
missed expression shape, or a disabled custom scan becomes an observable
unsupported-query error and cannot masquerade as a successful search.

\subsection{Why per-scan state was not optional}

The original file-static buffer appeared to work for one scan node.  A cross
join creates two scan nodes in the same backend, and repeated execution reuses
the process.  One node could move the global state to read-mode EOF while the
other still expected write mode.  An early EXPLAIN ANALYZE symptom was an
outer scan reporting one row where the fixture contained five.  Moving the
buffer, feature flags, output cursor, parameter state, placeholder nodes, and
pipeline description into \texttt{BioseqScanRuntime} gave each
\texttt{CustomScanState} an independent lifecycle.

The cleanup design also changed.  PostgreSQL errors use non-local jumps, so
ordinary C++ stack unwinding cannot be assumed at every boundary.  The
current normal path clears slots and closes providers in
\texttt{EndCustomScan}, while the registered \texttt{MemoryContextCallback}
deletes the runtime on context teardown and covers abort paths.  The callback
object itself lives inside the runtime whose lifetime it governs, so it is
registered once and not left pointing at a moved object.

\subsection{Why an owner needs a versioned ABI}

As join and slice support expanded, a simple target relation number was no
longer enough to identify the source of a helper.  Plan construction may
introduce resjunk columns, \texttt{INDEX\_VAR} references, subquery outputs,
or \texttt{PARAM\_EXEC} operands.  Current private tags carry a version and
fixed field count, while expression-bearing metadata travels through
\texttt{custom\_exprs}.  Plan finalization validates that the encoded
descriptor, target list, helper sites, and child outputs agree.  A mismatch is
reported as corrupted or unsupported plan state rather than decoded using an
older layout.

\subsection{Structured pipeline descriptions}

EXPLAIN output is derived from the runtime
\texttt{PipelineDescription}, which contains one description for each
selected stage.  The dispatch decision that selects minimization, chaining,
alignment, prefiltering, and accelerator policies also supplies this metadata.
A generic walker renders the resulting structure in textual and structured
PostgreSQL formats.

This design addresses a common observability failure: an execution path
changes, but EXPLAIN continues to print the old algorithm name.  The
dispatcher tests require runtime selection and description selection to
agree.  The custom scan augments that algorithmic description with database
facts such as owned-qual audit counters, projected columns, index
read/recompute decisions, storage hydration, submission counts, and fallback
reasons.

\section[PostgreSQL configuration parameters, prepared plans, and resource
safety]{PostgreSQL configuration parameters, prepared plans, and
\mbox{resource safety}}
\label{sec:customscan-safety}

\subsection{Configuration-parameter behavior}

BioSeqDB has settings that change storage/index policy, vectorized
qualification, column caching, mapper parameters, and custom-scan
availability.  They do not all have the same semantic status.

\begin{itemize}
  \item \texttt{bioseq.enable\_vectorization} changes the table-qualification
  route.  Current tests require identical match rows and require the custom
  scan to remain the owner in both states.
  \item \texttt{bioseq.enable\_column\_cache} changes a storage optimization,
  not alignment semantics.  The custom owner persists with the cache on or
  off.
  \item \texttt{bioseq.enable\_bioseq\_index\_scan} controls whether
  PostgreSQL index-scan paths participate in custom-scan planning.
  \item \texttt{bioseq.read\_sequence\_index} controls whether the mapper reads
  compatible stored per-sequence minimizers or recomputes them. Either policy
  retains the \texttt{BioseqScan} owner.
  \item Per-call aligner options override a snapshot of the session mapper
  settings for one owned expression.  This snapshot prevents a batch from
  observing a half-changed configuration.
  \item The master custom-scan setting controls whether the extension offers
  these owners.  Disabling the only supported owner does not authorize the
  Boolean body to return approximate or universally true results.  An
  attempted execution reaches the fail-closed boundary.
\end{itemize}

The tests that keep \texttt{BioseqScan} selected across these optimization
toggles are specifically a regression against the old cost-race design.
Changing a cache or vectorization setting may legitimately change the honest
cost estimate, but it must not resurrect an unowned executable copy of
\texttt{mmsearch}.

\subsection{Prepared statements and once-only evaluation}

Prepared and parameterized statements separate planning time from the values
seen at execution.  BioSeqDB keeps expression trees, source recipes, and
parameter coordinates in the plan, then evaluates operand \texttt{ExprState}
objects in the scan's expression context.  A constant query can be prepared
once, while a \texttt{PARAM\_EXEC} query is rebound for each rescan.  For a
join-level batch owner, query-child expressions are materialized once into
the query context before targets are streamed.

The exact operand is evaluated once at its authoritative boundary.  A lazy
slice is not recomputed separately for \texttt{mmsearch}, CIGAR, and
coordinate helpers.  Hidden child outputs and recipe identifiers let upper
nodes reuse the published value.  This is both a performance property and an
SQL semantics property for expressions whose evaluation can fail or whose
source lifetime is short.

\subsection{Memory contexts and ResourceOwners}

PostgreSQL uses memory contexts for bulk lifetime management and
\texttt{ResourceOwner} objects for relations, snapshots, buffers, and similar
resources.  A C++ destructor alone is insufficient because
\texttt{ereport(ERROR)} leaves a protected region through \texttt{longjmp}.
Conversely, deleting every C++ object only from a memory callback is too late
for resources that should be closed while their owner is still active.

The current scan uses a split protocol:

\begin{enumerate}
  \item \texttt{BeginCustomScan} constructs per-node runtime and registers one
  callback in the query memory context.
  \item \texttt{EndCustomScan} clears result and scan slots, removes
  parent-visible expanded-object references, closes sequence providers and
  access-method resources, and marks normal cleanup complete.
  \item The memory-context callback deletes the C++ runtime after normal end
  or performs abort-path deletion when execution did not reach
  \texttt{EndCustomScan}.
\end{enumerate}

The batch join applies the same principle to materialized query slots,
admission permits, locator providers, and both child plans.  It releases
tuple-visible references before resetting the arena that owns them.  These
details are necessary for repeated queries in one backend and for
\texttt{EXPLAIN ANALYZE}, which executes and then formats the same plan.

\subsection{Parallelism}

An SQL function can be declared \texttt{PARALLEL SAFE} while its custom owner
does not support parallel-aware execution.  The declaration permits the
function under PostgreSQL's parallel-safety rules.  It does not make a
scheduler, provider, accelerator queue, or materialized query child
transferable between workers.  BioSeqDB therefore disables parallel ownership
for shapes whose runtime cannot be partitioned safely.  The batch join also
rejects incompatible parallel children.  This prevents workers from sharing
mutable placeholders or provider state.

\section{Limitations and engineering trade-offs}
\label{sec:customscan-limitations}

The final owner protocol is deliberately narrower than arbitrary SQL.

\begin{enumerate}
  \item Join-level transformation currently targets INNER joins.  Base-owned
  searches can occur below other joins, but arbitrary outer-join
  \texttt{ON mmsearch(...)} semantics are not claimed.

  \item One semantic join-level \texttt{mmsearch} is accepted.  Stacked calls
  must be separated into query levels so that each has an unambiguous owner
  and match-row ABI.

  \item Row-security, security-barrier, pseudoconstant, volatile-sibling, and
  unsupported option-expression shapes are declined when the implementation
  cannot prove equivalent evaluation placement.

  \item Batch execution adds latency before the first row.  The base scan
  bounds that latency and memory with an 8192-submission rollover.  A raw
  batch join intentionally materializes its query child, so its cost and
  admission policy must account for that complete collection.

  \item Mutable placeholders are tightly coupled to PostgreSQL expression
  planning.  Every new result helper needs an OID mapping, a correctly typed
  placeholder, stable ownership metadata, population logic, EXPLAIN
  coverage, and join/aggregate tests.

  \item A custom scan is tied to BioSeqDB's table access and source-provider
  contracts.  An ordinary heap value or arbitrary function wrapper cannot
  automatically provide deferred fragment hydration, persistent-index
  compatibility, or batch-source lifetimes.
\end{enumerate}

These restrictions are preferable to implicit fallbacks.  A standalone
mapper can reject an unsupported command-line combination before processing
a file.  A database extension must additionally consider planner copies,
rescan, null extension, row security, volatility, and resource unwinding.
Failing closed makes that boundary explicit to the SQL user.

\section{Conclusion}
\label{sec:customscan-conclusion}

BioSeqDB presents sequence search through familiar typed SQL, but repeated
scalar calls do not implement its semantics.  The support function assigns a
large cost to unowned scalar evaluation.  Structural relation and join hooks
identify supported call shapes and establish exact ownership.  Plan
construction removes executable copies of the owned restriction.  The
executor then batches inputs and emits one projected row per alignment.

The result-injection mechanism began with ParadeDB's mutable score constant
and developed into a recipe-aware match ABI.  Typed placeholders populate the
fields summarized in Table~\ref{tab:match-placeholder-types} from one alignment
result.  \texttt{PlaceHolderVar} preserves placement and null-extension
semantics across joins and aggregates.  Hidden child outputs and setrefs-safe
metadata support slices and parameterized execution.

The decisive change from the proof of concept is not a smaller cost.  It is the
removal of cost as a correctness mechanism.  Current paths use finite,
nonnegative estimates.  Ownership is structural.  If a supported owner exists,
a path that would execute the same rendezvous restriction is not an alternative
implementation.  If no owner can be established, the SQL body reports the
unsupported shape instead of inventing alignment results.

This execution contract depends on stable, lazily readable source values and
bounded acquisition of their sequence bytes.
Section~\ref{sec:pg-storage-role} therefore turns from logical ownership to
physical representation.  It explains how parent rows, fragment locators, and
column streams make batched search practical inside PostgreSQL.
