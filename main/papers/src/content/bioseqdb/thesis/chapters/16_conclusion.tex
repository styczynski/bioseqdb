\section{What was built}

This thesis began with a practical question.  Could sequence alignment become
a database operation without reducing either side of the combination to a
thin wrapper?  The resulting BioSeqDB system shows that the answer is
qualified but affirmative.  PostgreSQL can own compact biological sequences,
relational metadata, persistent sequence indexes, and the lifecycle of an
alignment query.  The alignment engine can retain a recognizable
seed--chain--extend structure while operating on database-backed and lazily
composed sequence values.  The planner can replace a scalar-looking SQL
predicate with a batch-oriented custom scan.  CPU vector units and Vulkan
devices can be used where their data-shape and setup requirements are
satisfied.

The qualification matters.  BioSeqDB is not one algorithm and it is not one
unconditionally faster execution path.  It is a collection of explicit
contracts between representations, algorithms, storage, planning, and
runtime selection.  A compact sequence range states its alphabet and packing
geometry.  A minimizer representation states the widths and coordinates that
remain recoverable.  A chaining implementation states which predecessor set
and score semantics it evaluates.  A prefilter states the domain in which it
may reject a candidate.  A GPU route states its admissible batch geometry and
whether failure is allowed to fall back.  A generated SQL boundary states the
source entity, dependency, public symbol, and ownership policy from which an
installed object was derived.

The implementation built around these contracts can be read as five layers.
These are structural layers, not a second contribution list:

\begin{enumerate}
  \item The sequence layer represents packed, fragmented,
  PostgreSQL-backed, and lazy values through a common alphabet-aware access
  model.  Slicing, concatenation, reversal, letter extraction, and explicit
  materialization are expressed without requiring every consumer to accept a
  byte string.
  \item The alignment layer implements a minimap2-derived pipeline.  It
  extracts minimizers, finds seed hits, chains anchors, constructs regions,
  optionally prefilters mandatory gaps, extends selected regions, reconstructs
  CIGAR operations, and calculates final classifications and mapping
  qualities.
  \item The heterogeneous layer supplies Highway SIMD and Vulkan
  implementations for selected sketching, chaining, filtering, and extension
  work.  Admission, batching, resident state, and result proof are part of the
  route rather than hidden behind the same name.
  \item The database layer stores sequence fragments and index generations,
  loads input through bounded streaming paths, exposes remote providers, and
  turns alignment expressions into custom paths, plans, and scans.
  \item The boundary-generation layer derives SQL installation objects,
  fmgr entrypoints, row codecs, GUC bindings, catalog handles, and validation
  ledgers from structurally analyzed C++ sources.
\end{enumerate}

Together these layers are the principal contribution.  Any one kernel could
be called from PostgreSQL with much less work.  The difficult part is
preserving coordinate, lifetime, failure, and resource semantics across the
complete query.

\section{From the original pipeline to the final architecture}

The starting point was minimap2's mature long-read mapper
\cite{minimap2_paper}.  Its core is a
highly tuned imperative C pipeline over ASCII query strings, packed minimizer
records, an in-memory or \texttt{.mmi} reference index, scalar chaining, and
KSW2 extension.  Work is distributed over CPU workers.  Allocators and option
branches are organized around a standalone process.

BioSeqDB retained the underlying algorithmic decomposition because sparse
representative seeds, collinear chaining, and bounded extension concentrate
base-level work on plausible regions.  It did not retain the assumption that
all data starts as
an ASCII buffer or that one process owns the whole reference index.  It also
did not reproduce every minimap2 operating mode.  The implemented focus is
the sequence-search path used by the extension, not a byte-identical clone of
pairing, spliced alignment, rescue, and every command-line preset.

Table~\ref{tab:conclusion-transformation} summarizes the retained decomposition
and the changes made at each boundary.  Its extension and filtering rows refer
to Block Aligner, SneakySnake, and GateKeeper
\parencite{block_aligner_paper,sneakysnake_paper,gatekeeper_paper,gatekeeper_gpu_paper}.

Several intermediate designs were valuable because they exposed constraints
that shaped the final architecture.
Naive SIMD work exposed long dependency chains and data-rearrangement costs.
Per-query GPU submissions lost to command, fence, and allocation overhead.
GPU chaining without a resident upstream and downstream path moved too little
work to amortize the boundary.  A gather-heavy SneakySnake port preserved the
decision procedure but not its performance.  Loader overlap added queueing and
copy costs to a workload with too little independent work.  Persisting every
fragment independently increased first-query work and write pressure.
Cross-product template dispatch produced thousands of pipeline bodies before
the parameter space was collapsed around valid representation cells.

The retained designs share a pattern.  They move decisions to a boundary
where enough information is available.  Runtime configuration is converted
to a fixed pipeline specialization before the hot stages.  Accelerator work
is grouped by compatible batch geometry.  Target identity is used to reuse
resident state.  Fragment-native preparation can construct canonical
per-query anchors once and hand borrowed spans to the logical seed stage
without another allocation, copy, or global sort.  Mandatory and optional
alignment regions are distinguished before prefiltering.  Persistent index
generations in the opt-in grouped-publication route are accepted only after
format and compatibility validation. The checked-in MPF default instead uses
the legacy replace-in-place relation lifecycle described in Chapter 12.
PostgreSQL expression replacement is performed during planning, while per-row
values are installed during custom scan execution.  Generated SQL is accepted
only when the dependency and physical ledgers are complete.

Yes, but the common abstraction carries sequence symbols only as far as each
stage needs them. It is not a promise that every intermediate is a lazy
sequence. Table~\ref{tab:conclusion-rq1-stage-boundaries} gives the precise
boundary.

Thus, minimizer extraction and bounded alignment windows use the common
sequence data plane directly. Chaining deliberately does not because its
correct input is the anchor array, not letters. Eager whole-sequence
conversion is avoided for the implemented PostgreSQL and provider-backed
paths, while every unavoidable copy is explicit, interval-bounded, and
accounted by the access plan.

\paragraph{\textbf{RQ2.} Which scalar operations benefit from SIMD or GPU
execution, and which overheads move the break-even point?}
There is no backend-only answer. Benefit depends on:
\begin{itemize}
  \item sequence length and error profile.
  \item alphabet and intermediate representation.
  \item batch size.
  \item host and device residency.
  \item submission count.
  \item the amount of exact post-processing that remains on the host.
\end{itemize}
SIMD is most effective when loads are contiguous and lane work is uniform.
GPU speedups appear when many compatible jobs reuse resident inputs and keep
intermediate state on the device.  Small jobs and cold first submissions can
remain slower.  The final system therefore makes CPU, SIMD, and Vulkan routes
policy choices whose execution is observable.

\paragraph{\textbf{RQ3.} How can PostgreSQL plan and execute a set-valued,
batch-oriented search while presenting an ordinary typed SQL interface?}
Yes.  The ordinary \texttt{mmsearch} definition supplies PostgreSQL types and
a fail-closed direct-call contract.  Planner support and custom-path hooks
identify supported shapes, while the ordinary function's high cost makes
unowned scalar evaluation unattractive.  The resulting custom plan carries
the information required by \texttt{BioseqScan}.  Execution batches input rows
and may produce several alignment rows for one input.  Injected
\texttt{Const} and \texttt{Var} nodes allow filters, projections, and joins to
observe alignment fields without invoking an expensive scalar function for
each row.  \texttt{bioseq.edit} also fails closed without an owner, but the
other projection helpers return diagnostic sentinels if rewriting fails.
Exact ownership and placeholder rewriting therefore remain correctness
invariants.

\paragraph{\textbf{RQ4.} How should sequences, indexes, ingestion, external
data, caches, and generated boundary code fit around the kernels so that the
resulting system remains inspectable and reliable?}
The implementation provides strong mechanisms, but the result is not
uniformly complete. Important failures are made visible by:
\begin{itemize}
  \item opt-in versioned storage and legacy default MPF relations.
  \item explicit memory admission.
  \item bounded PostgreSQL loading.
  \item transaction-aware persistence.
  \item custom-scan ownership and plan-shape checks.
  \item hardware-only accelerator qualification.
  \item generated physical ledgers.
\end{itemize}
The chapter audits also identify places where an
option exists but is not wired, a footer is accumulated but not validated, a
provider path is partial, or a benchmark is a one-hit correctness gate rather
than exact row-set parity.  Inspectability requires reporting these facts,
not smoothing them into a single success claim.

\section{Limitations}

The first limitation is scope.  BioSeqDB is not a replacement for every
minimap2 command-line mode or every graph mapper.  Graph and de Bruijn
approaches are included to explain alternative representations, not because
the extension currently performs full variation-graph alignment.

The second limitation is heterogeneous completeness.
Table~\ref{tab:conclusion-performance-evidence} states the evidence boundary
for the recomputed and persisted GPU routes.  Work outside their admitted
shapes requires a CPU route or conservative acceptance where the relevant
filter permits it.

The third limitation is evidence comparability.  The reports summarized in
Table~\ref{tab:conclusion-performance-evidence} differ in source revision,
configuration, worktree state, and correctness predicate.  Their ratios
therefore remain route-specific evidence and are not pooled into a system-wide
speedup estimate.

A full benchmark attempt on 28 July 2026 terminated after writing an incomplete
\texttt{report\_193.json}.  The repository was dirty and the report was marked
ineligible for historical comparison
(\texttt{history\_eligible=false}).  Its raw evidence contains 123 records,
and the incomplete summary lists 40 regressions, 194 rule violations, and 84
sanity warnings.  The terminating strict-Vulkan sketch request was short by
8,210,340 bytes, approximately \(7.83\ \mathrm{MiB}\).  Because the run was
incomplete, none of its timing cells is used as current performance evidence.

\paragraph{Representation lifetime and SQL aggregate semantics.}
The proper-container specialization of
\texttt{compact\_sequence\_range} stores a \texttt{const R\&} but currently
accepts an rvalue. A temporary can therefore leave a dangling reference.
Until the constructor is deleted or constrained, or rvalues are moved into
owned storage, this specialization is lvalue-only. Its source object must
outlive every iterator and range use.

VectorAgg also has a semantic rather than merely performance-related
limitation. For empty or all-NULL supported input, current vector
\texttt{sum}, \texttt{min}, and \texttt{max} states can return zero, type
extrema, or date infinities where PostgreSQL returns NULL. PostgreSQL scalar
aggregation remains the semantic reference.
\texttt{bioseq.enable\_vectorization} is checked in with the default
\texttt{true}, so this defect is reachable for an eligible query under default
settings rather than being confined to an explicit experimental opt-in.
Until scalar parity is restored, deployments requiring PostgreSQL aggregate
semantics must disable vectorization. The affected rewrite must not be
described as interchangeable until regression tests establish scalar parity
for empty, all-NULL, mixed-NULL, and ordinary nonempty inputs across every
registered aggregate type and eligible plan shape.

\paragraph{Ingestion integrity and symbol preservation.}
Both active FASTA and FASTQ parsers invoke the compact encoder with
\texttt{unknown\_byte\_policy::DROP}. The exposed
\texttt{strict\_alphabet} option is not consulted. Loading an ambiguity such
as \texttt{N} into DNA4 can therefore delete that symbol, shorten the stored
sequence, and shift every later coordinate. This behavior is not alphabet
validation and must not be hidden inside an unqualified ``reliable loading''
claim. Until strict enforcement and diagnostics are wired, an input that may
contain ambiguity should use DNA5 or be validated and normalized explicitly
before loading. A production loader should also report per-record and total
dropped-symbol counts whenever permissive cleaning is requested.

The general file-reader defaults enable mmap, gzip detection, and parallel
gzip, with a \(16\,\mathrm{MiB}\) selection threshold.
\texttt{read\_sequences\_file} therefore auto-selects the custom
parallel-gzip decoder for qualifying gzip inputs. The decoder contains the
expected footer CRC32 and ISIZE fields and accumulates a running CRC, but no
current path compares the observed values with the footer. The
\texttt{parallel\_gzip\_verify\_crc} name therefore does not establish
end-to-end integrity. This is consequently an open integrity limitation on a
default-selected general-reader route, not merely on an explicit experimental
opt-in. PostgreSQL \texttt{bioseq.load} is a distinct path and retains zlib's
ordinary validation. Qualification of the custom route requires CRC32 and
ISIZE comparisons plus truncated, corrupted, concatenated-member, and
wrong-size tests. The PostgreSQL loader suite is also FASTA-centric. It does
not yet prove a FASTQ or gzip \texttt{bioseq.load} end-to-end case. Standalone
output paths further omit atomic replacement and full durability guarantees.

\paragraph{Privileged external-provider boundary.}
The external schema revokes public access because a SELECT may create outbound
traffic. Authorized provider scans should still be treated as privileged
experimental functionality. The locator firewall does not exhaust every
special-use address range or comprehensively classify IPv4-mapped IPv6
addresses. The implemented rate policy is not wired into requests and is not
cluster-wide. Most provider failures still collapse to SQLSTATE
\texttt{38000}. Cancellation can be delayed by blocking DNS resolution and
non-stop-aware retry sleeps. Production qualification requires a complete
public-address policy, cluster-wide quota enforcement, the documented
structured SQLSTATE mapping, and stop-aware DNS and backoff behavior in
addition to provider-specific capability tests.

Two current behaviors are result-completeness defects, not merely transport
limitations. First, lowering \texttt{= ANY(...)} predicates expands at most
64 equality combinations. Additional combinations are warned about but never
queried, and PostgreSQL residual filtering cannot reconstruct their rows.
Second, rows from successful provider/query pairs can suppress the first error
from a failed pair, so a mixed-success union can look complete. Both behaviors
can silently return an incomplete relation. Production qualification requires
one of two explicit contracts: fail closed on expansion overflow and on every
failed subquery, or return machine-readable completeness metadata that names
omitted combinations and failed pairs. Regression tests must cover more than
64 combinations, mixed success and failure, all-failure unions, and
de-duplication without error suppression.

Finally, database integration increases the amount of correctness surface.
PostgreSQL can abort through a non-local jump
\parencite{postgresql17_cpp_extensibility}.  The planner may rewrite expressions, a
custom scan may duplicate rows, and cached or persisted state may outlive the
statement that created it.  Generated fmgr and SQL ownership removes a major
source of drift, but it does not remove the need for SQL, lifecycle, and
failure-path testing.

\section{Future work}

The most valuable future work follows directly from the limitations:

\begin{enumerate}
  \item complete the authenticated persisted-format accelerator path so that
  eligible queries can keep minimizers, occurrences, anchors, chaining,
  windows, extension, and traceback on the device under one attested route.
  \item strengthen algorithm parity tests for RMQ predecessor admissibility,
  backtracking order, full emitted row sets, and all supported alphabet and
  coordinate widths.
  \item make the proper-container compact range reject or own rvalues, and
  restore VectorAgg scalar parity for empty, all-NULL, mixed-NULL, and ordinary
  inputs before enabling an affected rewrite.
  \item finish strict-alphabet enforcement and explicit dropped-symbol
  accounting. Wire gzip CRC32 and ISIZE validation, add corrupted-member
  tests, and prove multi-record FASTQ and compressed
  \texttt{bioseq.load} through PostgreSQL.
  \item harden standalone writer durability with an explicit temporary-file,
  flush, synchronization, and atomic-publication protocol.
  \item extend external providers with a complete public-address policy,
  cluster-wide rate limiting, cancellation-safe DNS and retry waits,
  credential handling, and uniform structured SQL errors. Make the
  64-combination expansion fail closed or expose explicit completeness
  metadata, and never suppress a failed provider/query pair merely because
  another pair returned rows.
  \item qualify the generated SQL and fmgr boundary across the intended
  PostgreSQL, operating-system, and architecture matrix.
  \item maintain benchmark qualifications as versioned evidence whose
  dataset, hardware, configuration, correctness predicate, and repository
  state are recorded together.
\end{enumerate}

\section{Closing perspective}

BioSeqDB's most important result is architectural rather than a single
speedup.  A sequence database cannot obtain trustworthy high performance by
placing an existing executable behind an SQL function.  It must understand
the representations, execution granularity, persistent state, and failure
semantics that make the executable fast and correct.  Conversely, an aligner
embedded in a database cannot ignore planning, transactions, row
multiplicity, memory contexts, and schema ownership.

The final system brings these concerns into one inspectable pipeline.  It
retains \mbox{minimap2}'s successful algorithmic decomposition
\parencite{minimap2_paper} and replaces process-local assumptions with explicit
sequence and index abstractions, and adds measured fragment-native CPU and SIMD
execution plus bounded heterogeneous routes.  PostgreSQL receives a
planner-visible batch executor.  The same ownership discipline extends to I/O,
external providers, cache coordination, and generated SQL boundaries.  The
result is an integrated experimental platform and a candid record of
intermediate outcomes, suitable for further scientific and systems work.
